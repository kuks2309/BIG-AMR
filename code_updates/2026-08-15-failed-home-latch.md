# 2026-08-15 — 실패한 호밍 뒤 bit15 로 조향이 열리던 구멍을 막는다

> 수정 이력의 기록처. 주석은 현재 코드의 사실만 담고 이력은 여기와 커밋 메시지가 담는다
> (`docs/claude_guideline/coding/conventions.md` §4).
> 결정 근거는 [ADR 2026-08-15](../docs/adr/2026-08-15-failed-home-latch.md).
> 약어: GUI(Graphical User Interface) · DI(Digital Input) · SDO(Service Data Object)

- 사용자 지시: 2026-08-15 "`~/home` 응답의 success 를 반드시 확인하고, 실패면 0° 를 쏘지
  마십시오. 드라이버가 막아주지 않습니다."
- 대상: `src/Comm/CAN/can_relay/can_relay/backend.py` · `test/test_backend.py`

## 먼저 — 지적 내용을 코드로 확인한 결과

| 주장 | 확인 | 근거 |
| --- | --- | --- |
| `homed_effective()` 가 `_homed=False` 여도 bit15 로 True | **맞다** | `backend.py:212-234`, `safety.py:102-106` (bit15 하나만 본다) |
| 드라이버가 안 막는다 | **맞다** | 조향 게이트 3곳이 전부 이 함수를 쓴다 |
| `~/home` 응답은 실패를 실패로 준다 | **맞다** | `HOMING_OK = frozenset({5})` (`link.py:78`) → ERR_GOZERO(10)은 `(False, …)` |
| 그 조합으로 지금 0° 를 쏘는 코드가 있다 | **없다** | `~/home` 소비자는 통합 GUI ROS2 탭 하나뿐이고 0° 를 안 쏜다 |

즉 **어긴 코드가 있어서가 아니라 막는 장치가 없어서** 문제였다. ADR 2026-08-08 §Decision 2 의
드라이버 쪽 `steer_to_zero()` 가 구현되는 순간 열리는 구멍이다.

## 실기 데이터가 말하는 것

```
호밍 결과  ERR_GOZERO (reached_mask=0x01)     ← node3 만 도달
node3      sw=0x9450 → bit15=1
node4      sw=0x9450 → bit15=1  pos=0  DI=9(−리밋)
```

`pos=0` 이 핵심이다. **시퀀서 경로에서는 비정상**이다 — 정상 완주면 축은 GOZERO 목표
(`7,882,020 / 7,859,062`)에 서 있다. node4 는 리밋에 그대로 있었고, 그 자리에서 0° 지령을
받으면 `7,840,086 counts ÷ 57,344 counts/° ≈ 136.7°` 를 움직인다.

⚠ 같은 `pos=0` 이 **판다 직결 경로에서는 정상**이다 — 그쪽은 GOZERO 단계가 없어 호밍이
리밋에서 끝나고 0° 복귀는 호스트 몫이다. 두 경로의 종료 위치가 다르므로 `pos` 하나로
성공/실패를 판정할 수 없다.

## 고친 것 — 실패 래치 `_home_failed`

「축을 움직여 놓고 성공으로 끝내지 못했다」를 인스턴스 상태로 들고, 그동안 bit15 를
조향 허용 근거로 쓰지 않는다.

| 지점 | 동작 | 위치 |
| --- | --- | --- |
| 세움 | 펌웨어가 시퀀스를 수리한 직후 | `home()` — `homing_start` 성공 뒤 |
| 세움 | 이동 프레임 송신 직전 | `_home_method35()` — `_homed=False` 옆 |
| 품 | terminal 이 `HOMING_OK` 일 때 | `home()` — `_homed = bool(ok)` 옆 |
| 품 | 재영점 확인됐을 때 | `_home_method35()` — `_homed=True` 옆 |
| 봄 | `_homed` 다음, 피드백 검사 앞 | `homed_effective()` |

**비관 기본값이다** — 축이 움직이기 시작하는 지점에서 세우므로 프로세스가 중간에 죽어도
래치는 서 있는 쪽으로 남는다. `_homed`(①)가 우선이라 성공 직후 스스로를 막는 일은 없다.

곁들여 고친 것 2개:

- **거부 사유가 이 경우 노드별 bit15 를 나열하지 않는다.** 전부 1 로 보이는 것이 정확히
  래치가 존재하는 이유다 — 나열하면 「bit15 는 1인데 왜 막지」로 오해를 키운다.
- **raw 경로(`set_motor_cmds`)의 note 에도 사유를 싣는다.** 종전에는
  `"node3 호밍 미완료 — 조향 거부"` 뿐이라 상위 모션이 원인을 구분할 수 없었다.
  이 경로가 게이트를 우회하지는 않았다(같은 `homed_effective()` 를 쓴다) — 말이 부족했다.

`snapshot()` 에 `home_failed` 를 실어 진단에서 보이게 했다.

## 왜 다른 안을 안 썼나

- **`homed_effective()` 에서 bit15 를 빼기** — Seer 호밍 인정이 깨진다. 2026-08-04 에 그것
  때문에 바퀴가 한 카운트도 안 움직인 실기 사고가 있었고 `README.md:237` 이 「재호밍 불필요」를
  약속한다.
- **호출부가 응답을 확인하게 하기** — 지금 필요한 규율이지만 강제가 안 된다. 다음 호출부가
  생기면 같은 구멍이 다시 열린다. (배타적이지 않다 — `steer_to_zero()` 구현 시 성공 분기
  강제는 여전히 해야 한다.)
- **bit15 0→1 전이로 「누가 재호밍했다」를 감지해 풀기** — 폴 주기(50 ms)보다 짧은 전이를
  놓치면 조용히 안 풀리고, 안 놓치면 조용히 풀린다. 어느 쪽 실패도 화면에 안 드러난다.

## 치르는 값

**Seer 가 복구 호밍을 해도 래치는 안 풀린다.** 우리가 관측할 수 없는 사건이라 근거로 치지
않기 때문이다. 해제는 `~/home` 재수행뿐이고 그건 **100°+ 물리 스윙**을 동반한다.
운용에서 이게 실제로 걸리면 「운용자가 축 위치를 확인했다」를 명시적으로 받는 해제 경로를
추가한다 — 근거 없이 자동으로 푸는 경로는 만들지 않았다.

### 실기 기록 (통합 GUI + `can_relay_node`, 기체 Foil_A082)

호밍을 원점 탐색(WAIT) 중에 `~/home_cancel` 로 끊어 실패시켰다.

```
13:53:23  호밍 실패 — ERR_ABORT (24s, reached_mask=0x00)
          node3  pos=0  sw=37968(0x9450)  homed=True   di=9(−리밋)   ← 17시와 같은 값
          node4  pos=0  sw=4176 (0x1050)  homed=False  di=1
13:54:53  지령 거부 — 직전 호밍이 끝을 못 봤다 — 축이 0° 에 서 있다고 볼 수 없다. …
```

⚠ **이 취소는 래치를 단독으로 증명하지 않는다** — node4 의 bit15 가 0 이라 래치 없이도
막혔을 상태다. 구분한 것은 **문구**다(래치가 없으면 「N4 bit15=0」이 나온다).
두 축 모두 bit15=1 인 채로 실패하는 조합은 GOZERO 단계에서 끊어야 하는데, 재시도 시
두 축이 이미 홈이라 펌웨어가 재탐색을 건너뛰어 **3초 만에 DONE** 이 나 창이 없었다.

해제 경로는 그대로 확인됐다.

```
호밍 재수행 → DONE (3s, reached_mask=0x03) → home_failed=False
node3 pos=7,882,022   node4 pos=7,859,065      ← 펌웨어 GOZERO 상수 ±3 counts
조향 0° 지령 → 수리(거부 0건)
node3 pos=7,871,818   node4 pos=7,840,092      ← 0° 기준 +3 / +6 counts
```

**부수 확인** — 그동안 계산값이던 GOZERO 정착 편차가 실측으로 맞았다:
`(7,882,022 − 7,871,815) / 57,344 = +0.178°` · `(7,859,065 − 7,840,086) / 57,344 = +0.331°`.

**미검증으로 남는 것**: 두 축 bit15=1 상태의 실패, 그리고 그때 뜨는 새 상태줄
「조향 잠금 — 직전 호밍 미완료」. 축을 홈에서 떼어 놓고 다시 호밍해야 창이 생긴다.

## 남는 것

- `steer_to_zero()`(ADR 2026-08-08 §Decision 2) 미구현 — `stash@{0}`. 구현 시 **성공 분기
  강제는 별도로** 해야 한다. 이 래치는 게이트를 닫을 뿐 호출부가 응답을 읽게 만들지 않는다.
- **함수표 이중 기록을 못 했다.** `can_relay` 모듈 로컬 함수표
  (`src/Comm/CAN/can_relay/docs/function_table.md`)는 **타 세션이 오늘 작성 중인 미커밋
  파일**이라 origin/main 에 없다. 그 세션이 커밋하면 `homed_effective`(#7)·`home`(#19)·
  `_home_method35`(#17)·`snapshot`(#20) 행과 인스턴스 상태표에 `_home_failed` 를 반영해야
  한다. 루트 집계에는 이번 변경을 등재했다.
- 판다 직결·단독 GUI 는 이 게이트를 안 지난다(시퀀서 미사용, 완료 판정이 bit15 2상 관측뿐).
## ⚠ 래치는 프로세스 안에만 있다 — 재기동이 지운다 (닫힘)

`_home_failed` 는 인스턴스 상태라 드라이버가 죽으면 소멸한다. 같은 날 다른 세션이 넣은
감시 노드(`supervisor.py`, `76b3612`)가 「직전이 engaged 였다」를 근거로 `~/engage true` 를
자동 호출하므로, 그것만 있으면 새 프로세스가 래치 없이 떠 축이 어중간한 자리에 있어도
bit15 만으로 조향이 열린다.

**그 세션이 같은 구멍을 함께 닫았다** — `health.py:196-203` 이 진단의 `home_failed` 관측을
복귀 차단 사유로 든다(`HOLD`). 그래서 부채로 등록하지 않는다.

```
if obs.cur.get("home_failed"):
    return HOLD, "직전 호밍이 끝을 못 봤다(조향 잠금) — 재기동이 그 래치를 지우므로 …"
```

⚠ 남는 전제 하나: **진단이 도달할 때만** 성립한다. 진단이 두절된 채(`DEAD`) 재기동되면
관측이 없어 이 차단이 걸리지 않는다. 그 경로는 아직 확인하지 않았다.
