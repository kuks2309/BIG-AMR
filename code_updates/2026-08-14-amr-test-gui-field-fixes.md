## ① 조향이 단발 송신이라 한 축이 지령을 통째로 놓쳤다

**증상**(11:06:34~11:06:40) — 「좌후 45°」에서 조향 `+45°` 를 지령했는데 N4 가 **한 카운트도
움직이지 않았다.** SDO 거부 로그도 없었다.

```
11:06:29  '좌전 45°' — 조향 -45° 지령 → 정착 성공 (두 축 −45°)
11:06:34  '좌후 45°' — 조향 +45° 지령 → 정착 실패
11:06:40  실측 N3 +44.99999 / N4 −45.00003     ← N4 가 직전 값 그대로
```

화면도 같았다(Front +45.0° / Rear −45.0°). Seer 표는 부호 반전 규약대로 F.S −45 / R.S +45 로
같은 사실을 보였다. 중간값이 아니라 **직전 값 그대로**였으므로 그 축은 지령을 받지 못했다.

**원인** — `_steer_axis` 가 `0x607A`+`0x6040=0x3F` 를 한 번만 보내고, 폴 루프는 구동(`0x60FF`)만
재송신했다. 프레임 한 장이 유실되면 그 축은 지령을 통째로 못 받는다. 같은 증상이 이식본
(`can_relay/ui/backend_direct.py`)에서는 이미 재송신으로 해결돼 있었고 원본만 남아 있었다.

**수정** — 조향 목표를 상태(`_steer_counts`)로 남기고 폴 루프가 매 주기 재송신한다.
호밍 중에는 보내지 않는다(드라이브 내부 루틴과 같은 축을 다투지 않게). 정지는 그 목표를
비워 **재송신을 그친다** — 새 프레임을 보내는 것이 아니다.

## ② 호밍 후 0° 복귀 판정이 조그 정지 래치에 삼켜졌다

**증상**(11:06:01) — 두 줄이 **같은 초**에 찍혔다. 10초를 기다린 적이 없다.

```
11:06:01  원점 확인 — 원점 신호 확인(50초 소요).
11:06:01  호밍 미확인 — ... 10초 안에 ... (N3 실측없음 · N4 실측없음)
```

**원인** — `_wait_settle` 은 `_jog_stop` 이 서 있으면 즉시 `False` 로 빠진다. 그 플래그는
**정지 버튼이 세우고 다음 조그가 시작될 때만 내려가는 래치**라, 11:01:44 에 조그를 정지한
값이 그대로 남아 호밍 경로를 막았다. 0° 지령은 나갔지만 **판정이 시작조차 못 했다** —
기능 실패가 아니라 판정 실패다.

**수정** — `_wait_settle(honor_jog_stop=)` 인자 신설. 호밍은 조그가 아니므로 0° 복귀는
`False` 로 부른다. 조그 경로는 그대로 래치를 본다.

**실기 재확인**(11:16) — 22초 만에 원점 확인 후 **4초 기다려 ±0.1° 안 도달**을 판정했다.

```

11:16:43  원점 확인 — 원점 신호 확인(22초 소요).
```

## ③ 굳은 Seer 값과 매 표본 대조해 거짓 경보를 냈다

**증상**(11:16:03) — 제어권을 잡은 직후, 아무도 축을 움직이지 않았는데 45° 불일치 경보.

```
11:16:02  ⚠ 제어권 획득 — 릴레이 intercept, Seer 에서 가져옴
11:16:03  ⚠ N3 조향 기준 불일치 5회 연속 — Seer -89.99° 인데 CAN 실측 -45.00° (차 +44.99°)
11:16:05  조그 '좌후 45°' …                    ← 우리 첫 조향 지령은 그 뒤였다
```

**원인** — **제어권을 쥐면 Seer 는 모터를 못 읽는다**(릴레이가 intercept 로 넘어가 판독이 굳는다).
그런데 대조를 멈추는 조건이 「제어권 보유」가 아니라 「우리가 조향을 보냈는가(`_steer_commanded`)」
였고, 그 플래그는 제어권을 잡을 때 다시 열렸다. 게다가 대조를 부르는 `_set_meas` 는 폴링 중,
즉 **제어권 보유 중에만** 돈다 — 그 대조에는 유효한 창이 애초에 없었다.

**수정** — 대조 상대를 **잡기 직전에 읽어 둔 Seer 각도**(`_seer_at_take`)로 바꾸고, 비교 대상은
**획득 후 처음 들어온 신선한 CAN 실측**으로 한정해 **축별 세션당 1회**만 본다. 그 시점에는
아직 아무도 축을 움직이지 않았으므로 둘은 같은 자세를 가리켜야 한다.

죽은 코드도 함께 걷어냈다 — `SEER_MATCH_STREAK` · `SEER_MATCH_REWARN_S` 상수와 축별 연속
카운터·재경보 시각 상태 2개.

## 부수 확인 — 호밍 중 각도 칸이 `—` 인 것은 설계다

사용자 질문: 「호밍에서 왜 rpm 은 나오는데 각도가 안 나오나」.

호밍 중 `0x6064` 는 실위치가 아니라 **0** 을 돌려주므로 그 구간의 각도는 갱신하지 않는다
(`_on_motor_data`). 회전(`0x606C`)·전류(`0x6078`)는 그런 제약이 없어 그대로 나온다 —
화면의 `−249.5 / −250.6 rpm` 이 조향축이 실제로 리밋을 찾아 돌고 있다는 증거다.

같은 날 오전에 고친 `_fill_row`(`None` 을 `—` 로 덮어쓰기) 덕에 이제 그 구간이 `—` 로 보인다.
종전에는 호밍 직전 각도가 그대로 남아 있어, 축이 250 rpm 으로 도는 동안에도 화면은 옛 값을
보여줬다.

## ④ 중복 실행 가드 (사용자 요청)

`acquire_single_instance()` 신설 — `/tmp/amr_test_gui.lock` 에 `flock(LOCK_EX|LOCK_NB)`.
`main()` 이 **창을 만들기 전에** 확인하고, 잠겼으면 선점자 PID(Process ID)를 알려 준 뒤 `1` 을 반환한다.

판다는 한 프로세스만 열 수 있다. 두 창이 동시에 USB 를 잡으면 나중 창의 연결이 계속 실패하고,
먼저 잡은 쪽이 무엇을 하는지 화면으로는 알 수 없다.

**`flock` 을 쓴 이유** — 프로세스가 죽으면 커널이 잠금을 자동으로 푼다. PID 파일만 두면 비정상
종료 뒤 찌꺼기가 남아 다음 실행을 영영 막는다. 잠금 파일에 PID 도 적어 「누구를 봐야 하는지」를
알려 준다.

실동작 확인:

```
$ can_relay          # 두 번째 실행
[gui] 이미 실행 중입니다 (PID 596760) — 그 창을 쓰십시오.
      판다는 한 프로세스만 열 수 있어 두 창이 동시에 USB 를 잡으면 둘 다 못 씁니다.
$ echo $?
1
```

회귀 5건 신설(`test/test_single_instance.py`): 첫 호출이 잠금·PID 기록 · 두 번째는 선점자 PID 와
함께 거부 · 선점자가 닫히면 해제 · **찌꺼기 PID 파일이 막지 않음** · `main()` 이 실제로 가드를
부름(배선). 돌연변이(가드 무시)로 배선 시험 1건 실패 확인.
