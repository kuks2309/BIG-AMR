## §8 호밍 1회차 실행 결과 (2026-08-03 09:58) — **ERR_TIMEOUT, 축 무반응**

실행: `orin_home_experiment.py --repeat 1` · 캡처 `Log/home_experiment_260803_095815.jsonl` (66,614 프레임, 125.4 s)

### 8-1. 관측

| 항목 | 결과 |
|---|---|
| FSM 진행 | ENABLE(0.00s) → SET_SPEED(0.11) → START(0.22) → **WAIT(0.33) → ERR_TIMEOUT(120.26)** |
| `done_mask` / `reached_mask` | 전 구간 `0x00` |
| 조향 `0x6064` | 전·후 모두 **0** (변화 없음) |
| DI3 / DI4 | 전 구간 `0x03` / `0x01` (변화 없음) |
| **statusword** | **125초 내내 변화 0건** — node3·4 `0x9450` (788/787 샘플), node1·2 `0x8050` (304/305 샘플) |
| SDO ABORT | **0건** |

**호밍 프레임은 설계대로 정확히 발행됐다** (t=1.048 s, node3·4 각 1회):
`0x6040 = 0x86` → `0x6099 = 2500` → `0x60FB:04 = 1`

### 8-2. 근본 원인 — 드라이브가 `Switch on disabled` 를 벗어나지 못한다

statusword `0x9450` / `0x8050` 은 둘 다 **bit6 = 1 = `Switch on disabled`** (bit3 Fault=0, bit4 Voltage enabled=1).
CiA402 상태기계에서 이 상태를 벗어나려면 **Shutdown = controlword `0x06`**(bit1 EV=1, bit2 QS=1, bit0 SO=0, bit3 EO=0, **bit7 FR=0**)이 필요하다.

| 발신자 | controlword | 왜 안 먹는가 |
|---|---|---|
| **우리 펌웨어** ENABLE 단계 | `0x86` (`safety_seer_gate.h:219,362`) | `0x06` + **bit7(Fault reset)=1**. Fault reset 이 우선 해석되어 Shutdown 이 성립하지 않는다 |
| **Seer** (전 구간 96회, t=1.05~125.35 s) | `0x3F` | `Enable operation`+setpoint. `Switch on disabled` 에서는 **무효** — `0x06` 부터 밟아야 한다 |

⇒ **둘 다 `0x06` 을 보내지 않는다.** 그래서 축이 살아나지 않고, `0x60FB:04=1` 도 무시되며,
`0x6041` bit15 가 1→0 으로 떨어지지 않아 FSM 의 `seen_active` 가 영영 서지 않는다(→ 120 s 타임아웃).
**펌웨어 WAIT 로직(0→1 전이만 완료로 인정)은 정확히 동작했다** — 결함은 그 앞단이다.

### 8-3. ★ 드러난 펌웨어 결함 — 호밍 시퀀서에 암묵 전제가 있다

`seer_homing_tick()` 의 ENABLE 단계는 **「드라이브가 이미 `Operation enabled` 이다」를 전제**한다.
2026-07-27 캡처에서 호밍이 성공했던 것은 그때 Seer 가 축을 이미 enable 해 둔 상태였기 때문이며,
그 전제는 **코드·문서 어디에도 기재돼 있지 않다.**
서보 off 상태에서 호밍을 걸면 **120초를 소모하고 실패한다** — 지금 실측된 그대로다.

### 8-4. ★ §7-2 가설은 **반증됐다** (자기 정정)

§7-2 에서 「`0x6064`=0 은 드라이브 미-enable 구간의 현상일 수 있다」고 세웠으나, 본 회차가 이를 뒤집는다:

| 노드 | statusword | 상태 | `0x6064` |
|---|---|---|---|
| node1·2 (구동) | `0x8050` | **Switch on disabled** | **−655,844 / −650,517 (실값)** |
| node3·4 (조향) | `0x9450` | **Switch on disabled** | **0** |

**같은 `Switch on disabled` 인데 구동축은 실위치를 반환한다.**
⇒ 조향축의 `0x6064`=0 은 enable 여부와 **무관**하며, 원인은 **여전히 미판정**이다.
debt-007 을 낳은 관측들을 하나로 통합하려던 §7-2 시도는 폐기한다.

부수로 확인된 것: `0x6041` bit15 는 **구동축(호밍 안 함)에서도 1** 이다(`0x8050`).
따라서 bit15 를 단독으로 「호밍 완료」라 부르는 것은 부정확하고, 의미가 있는 것은 **0→1 전이**뿐이다

### 9-3. ★ `0x6064` = 0 은 **전원 사이클로 풀렸다** — 원인이 새로 좁혀졌다

| 시점 | node3·4 statusword | node3·4 `0x6064` |

## §12 Seer 조향각 채널 2종 — 1005 발견과 1040 의 정체 확정 (2026-08-03 12:4x)

사용자가 `2026-08-03_조향각-1005-조회경로.md` 를 지목했다. **SEER API 1005(Query Robot Speed)** 의
`steer_angles` 가 조향각이며, 이 프로젝트의 RoboshopPro 화면 다이얼이 그 값이다.

### 12-1. 실측 — 세 채널 동시 30 s 샘플링 (송신 0건, 판다 SILENT·passthrough)

| 채널 | 상이값 | 관측 |
|---|---|---|
| CAN `0x6064` | **2개** (6 counts 디더) | node3 7,871,823 ↔ 7,871,817 · node4 7,840,052 ↔ 7,840,058 |
| **1040** `motor_info.position`(type=1) | **2개** | 디더 간격이 **정확히 6.0000 counts** |
| **1005** `steer_angles` | **1개** — 102 샘플 전부 `(-0.0, 0.0)` | 디더를 **전혀 추종하지 않음** |

### 12-2. ★ 1040 의 정체가 확정됐다 — §11-1 반증이 실측으로 재확인

**1040 은 `0x6064` 의 아핀 변환이다.** 디더가 counts 단위로 일치하고 기울기 × 57,344 = 1.0000000(7자리).
⇒ `0° = CAN + Seer°×57344` 는 **항등식**이며 자세와 무관하게 **Seer 내부 영점 상수**를 돌려준다.
§10 의 「독립 경로 교차검증」·「2회 독립 실행 일치」·「사용자 0° 확인이 이상적 조건」은 **전부 무효**다(§11-1).
도구 출력도 「0° 추정」 → **「Seer 영점 상수」** 로 라벨을 바꿨다(`orin_steer_crosscheck.py`).

### 12-3. ★ 1005 는 **다른 채널**이다 — 다만 전달함수 미확정

같은 시각 1040 이 node4 **+0.000605°(≈35 counts)** 이탈을 보고할 때 1005 는 **정확히 `0.0`** 이었고,
6-counts 디더도 잡지 않는다. ⇒ **1040 과 같은 데이터가 아니다.**

벤더 정의 [`T-Robot_seer_gui/references/seer/robokit-api/robot-status-api/005-query-robot-speed.md:40-41`] (타 저장소 github kuks2309/T-Robot_seer_gui — 본 저장소 `References/` 아님):
- `steer_angles` = "The **current** steering angle of the multi-steering wheel robot … sorted according to the order in the model file, unit: rad" ⇒ 듀얼이면 **[front, rear]**
- `r_steer_angles` = "Steering angles **received**" ⇒ 지령값(실측 아님)

**⚠ 모르는 것 — 인용 시 반드시 병기:**
- **분해능·산출 방식이 벤더 문서에 없다.** 원시 엔코더인지 감속비 보정·융합값인지 미기재
  (사용자 문서도 같은 지점을 `[미확인]` 으로 표시했다).
- 현재 말할 수 있는 **하한뿐**: 1040 이 35 counts 이탈을 보고하는 자세에서 1005 가 `0.0` 이므로,
  같은 영점·단순 반올림 가정 시 **양자화 > 70 counts(0.0012°)**. **상한은 미지.**
- ⇒ **정지 상태에서는 1005 와 1040 을 구분할 수 없다.** 조향을 실제로 움직여
  **1005 의 계단을 관측해야** 전달함수가 나온다.

### 12-4. 왜 이것이 중요한가

§11 이 남긴 최대 공백은 ~~**「물리적 직진에 대한 非-Seer 앵커가 없다」**~~였다.

> ❌ **재정정 2026-08-03 17:30: 그 「공백」 서술 자체가 틀렸다.** 물리 직진 앵커는 **실재한다**
> (Seer 의 EasyDRIVE `steerOffset` 교정 조향각 + 사용자 육안 확인 — 바퀴 직진 상태에서 Seer
> 앞바퀴 2축 0°, 2026-08-02 · 2026-08-03, `can_relay` GUI 동일). 실제 공백은
> **앵커의 정밀도(육안 ≈±1° = ±57,344 c)가 counts 소수 자리(193 c = 0.0034°)에 못 미친다**는 것이다.
> 아래 「1005 가 독립 앵커인가」 논의는 **두 Seer 채널 간 독립성** 문제로만 유효하다.
1005 는 그 공백을 **메울 수도, 못 메울 수도** 있다:
- 1005 가 `0x6064` 와 **다른 산출 경로**(예: 조향 모터 별도 엔코더·융합)라면 → 부분적 독립 앵커가 된다.
- 1005 가 결국 같은 엔코더를 거칠게 반올림한 것이라면 → 앵커가 아니다.
**둘 중 무엇인지는 스윕 실측으로만 갈린다.** 그전까지 1005 를 「독립 검증」이라 부르지 않는다.

⚠ 함의 하나: **사용자의 "Seer 에서 0도" 확인은 1005 를 본 것**이며, 1005 는 이 자세에서 `0.0` 을
보고한다. 그러나 1005 의 양자화가 미지이므로 그 확인이 **몇 counts 를 보증하는지 알 수 없다.**
§10-1 이 이를 「외삽이 거의 없는 이상적 조건」이라 부른 것은 **여전히 무효**다.

### 12-5. 반영

`Tools/docking_field_kit/orin_steer_crosscheck.py` 가 이제 **3채널을 함께 기록**한다:
`src="can"` · `src="seer"`(1040) · `src="seer1005"` · `src="seer1005_cmd"`(r_steer_angles).

### 16-3. 덤으로 확정된 것 3가지

1. **`−Limit` 실측 재현** — 리밋 도달 순간 DI3/DI4 가 `0x01` → **`0x09`**(bit3=1).
   기준선#4(리밋 스위치 실재, `0x6000` sub1 bit3 = −Limit)를 이번 회차가 **직접 재현**했다.
2. **탐색 시간 ≈33 s** (10° 지점 → −리밋). 2026-07-27 캡처의 ≈31 s 와 정합.
3. **★ GOZERO 편차 실측** — 호밍 완료 직후 위치가 **node3 `+0.178°` · node4 `+0.331°`**.
   그동안 계산으로만 주장하던 값이 **실측으로 확인**됐고, 재계산했던 **`+0.331°` 가 정확히 맞았다**
   (폐기된 `+0.334°` 는 구 0° 기준 잔재였다 — §11-4). **debt-034 의 근거가 실측으로 굳었다.**

### 16-4. 부수 — 판독 경로 결함 1건 발견·수정

실험 직전 dry-run 이 `n3 sw=0x1050 bit15=0 · n4 pos≈19` 를 읽었는데, 같은 시각 45 s 수동 청취
(4,589 샘플, `Log/observe_144335.jsonl`)는 **양 노드 `0x9450`·홈 고정**이었다. 3회 재실행에서는 재현되지 않았다.

**원인**: `sdo_read()` 가 요청 전 수신 버퍼를 비우지 않아, **제어권 보유 중에도 bus2 로 전달되는
Seer 폴의 응답**(`cmd==0x40` → `bus_fwd=2`)을 내 요청의 답으로 **간헐 오인**했다.
적대적 검증 F2 가 지적한 오염과 같은 계열인데, heartbeat 를 고친 뒤에도 **응답 매칭이 느슨해** 남아 있었다.

**수정**: ① `sdo_read()` 가 요청 직전 수신 버퍼를 비운다(비운 프레임도 로그에 남긴다).
② `snap()` 을 단발 판독 → **5회 중앙값/최빈값**으로 교체.
⚠ **오늘 이전에 단발 `sdo_read` 로 얻은 값은 이 오염 가능성을 안고 있다** — §15 판독은 45 s 수동 청취와
교차 일치하므로 유효하나, 그 외 단발 판독 인용 시 주의.

### 16-5. 사용자 지적 — release 경고가 과했다

*"seer가 오류가 있을때만 재호밍을 하고, 제어권을 반환하면 아마 제어권 전 각도 홀딩 명령어를 계속 줄 것임"*
— 관측과 정합한다. 45 s 청취에서 Seer 는 `0x607A = 7,840,086`(홈)을 **계속 홀딩 지령**했고 재호밍은 없었다.
⇒ `Rig.release()` 의 「Seer 가 재호밍을 개시할 수 있습니다」 경고는 **오류 상황 한정**으로 좁혀야 한다.

## §17 ★★ §15-4·§16 반증 (2026-08-03 15:25) — 원인은 「이미 홈」이 아니라 `0x6064` 래치다

펌웨어 수정본 플래시 후(`DEV-cc5e0491-DEBUG`, 서명 대조 ★일치) **홈 상태에서 호밍을 걸었다.**

### 17-1. 실측 — 홈에서도 호밍은 정상 동작한다

`orin_homing_edge_test.py --offset 0` · 산출 `Log/homing_edge_260803_152520.json`

| t | 사건 |
|---|---|
| **0.307 s** | node4 `bit15` **1→0** ← **하강 에지 발생** |
| 0.320 s | node3 `bit15` 1→0 |
| **31.311 s** | node4 `bit15` 0→1 · **DI `0x09`(−Limit)** ← 축이 실제로 리밋까지 갔다 |
| 34.90 s | **DONE** |

**축이 홈에 있는데도 −리밋까지 주행했다.**
⇒ §15-4·§16 의 「축이 이미 홈이면 드라이브가 무동작 즉시 완료한다」는 **반증**된다.
Handbook §4.6 의 *"already in the resetting position … directly outputs the resetting end signal"* 은
이 드라이브의 이 조건에서는 발현하지 않는다(적어도 홈 ±0.001° 에서는).

### 17-2. 09:58 실패와의 진짜 차이 — `0x6064` 래치 하나뿐

| | 09:58 (ERR_TIMEOUT) | 15:25 (DONE) |
|---|---|---|
| statusword | `0x9450` | `0x9450` — **같음** |
| `0x6098` 호밍 방식 | 1 | 1 — 같음 |
| 조향 위치 | 홈 | 홈 — 같음 |
| CiA402 상태 | Switch on disabled | Switch on disabled — 같음 |
| **`0x6064` 보고** | **0 (래치)** | **실값 7,871,815** |

⇒ **실패의 원인 후보는 `0x6064`=0 래치, 즉 debt-036 이다.** 그 상태에서는 호밍이 걸리지 않는다.

### 17-3. 내가 어디서 틀렸나 — 교란 변수 미통제

14:46 실험(10° 떼고 호밍 → 성공)을 보고 **「홈에서 떼어놔서 성공했다」**고 결론냈다.
그러나 그 시점은 **11:38 리부팅 이후**로 `0x6064` 래치가 **이미 풀려 있었다.**
즉 「오프셋」과 「래치 해제」 두 변수가 동시에 바뀌었는데 **오프셋만 원인으로 귀속**했다.
`--offset 0` 대조군을 그때 함께 돌렸으면 바로 갈렸을 것이다.

이것은 `docs/claude-mistake/INDEX.md` §메타 패턴의 **「하나를 보고 단정」** 재발이며,
같은 세션에서 적대적 검증이 이미 여러 번 잡아낸 유형이다.

### 17-4. 펌웨어 수정의 현재 지위 — 무해하나 필요성 미확인

추가한 「이미 홈」 종료 조건은 이번 회차에서 **발동하지 않았다**(하강 에지가 정상 발생해
`seen_active` 가 섰으므로 athome 경로는 타지 않는다).

- **무해함은 실증됐다** — 정상 호밍 경로가 그대로 동작했다(DONE 34.9 s, 위치 확인 조건 4개가 정상 경로를 건드리지 않음).
- **필요성은 미확인** — 「드라이브가 무동작 즉시 완료」 상황이 실재하는지 아직 못 봤다.
- ⇒ **되돌리지 않는다**(무해 + 방어적). 다만 **「이 수정이 09:58 실패를 고쳤다」고 주장하지 않는다.**

### 17-5. 도구 결함 — 판정 문구가 조건을 안 본다

`orin_homing_edge_test.py` 의 판정이 `--offset 0` 인데도 「홈에서 떼어놓으니 동작했다」고 출력했다.
`final_state` 만 보고 `offset` 을 보지 않는다. **정정 대상.**

### 17-6. 다음 — 래치 재현이 유일한 길

지금은 래치가 풀려 있어 재현이 안 된다. debt-036 상환계획 ① 대로
**제어권 취득 / 호밍 시도 / CAN 단절 / 서보 off↔on 을 1변수씩** 바꿔가며 래치 진입 조건을 찾아야 한다.
매 관측에 **`0x6041` 전체 · `0x6000:01` · `0x603F` · `0x6064` 를 동시 취득**한다.
