사전 인벤토리다. 결함 평가는 포함하지 않는다.

## 목적

브라우저에서 라인 인식을 눈으로 확인한다 — 카메라 영상 위에 `/line/error` 의 중심선·제어점·
수치를 겹쳐 보여주고, 전진/후진 카메라를 화면에서 전환한다.

## 핵심 제약 — 서버는 픽셀을 만지지 않는다

`cctv_webview` 와 같은 규약이다. 카메라가 준 JPEG 를 **디코드 없이** multipart MJPEG 로 흘리고,
오버레이는 **브라우저가** 그린다. 서버가 그리려면 디코드·재인코딩이 필요해 전제가 무너진다
(720p 실측 6.55 ms/frame). 실제로 `line_seg_node` 의 `/line/debug_image` 를 구독하면 인식률이
24.4 → 2.3 Hz 로 떨어진다(2026-08-14 실측) — 이 뷰어가 그 경로를 쓰지 않는 이유다.

## 중복 확인 (coding.md §2)

| 후보 | 기존 유사물 | 판정 |
| --- | --- | --- |
| JPEG 프레임 저장 | `cctv_webview.frame_store.FrameStore` | **재사용**(import) — 복제하면 두 벌이 갈라진다 |
| MJPEG 스트리밍 핸들러 | `cctv_webview.server` | **복제하지 않고 최소 재구현** — 화면 구성(타일 격자 vs 단일 영상+오버레이)과 엔드포인트가 달라 공유 이득이 적다. 스트리밍 루프 로직만 같은 형태 |
| 디버그 오버레이 | `line_seg_node` 의 `/line/debug_image` | **쓰지 않는다** — 서버측 재인코딩이 인식률을 10배 떨어뜨린다(실측) |
| 방향 전환 | `line_follow` 액션의 `reverse` goal | 별개 — 이 뷰어는 **인식 노드**의 카메라만 바꾼다. 제어는 관여하지 않는다 |

## 검증 (구현 직후 · 실카메라)

| 항목 | 결과 |
| --- | --- |
| colcon 빌드 | `line_webview` 오류 0 |
| 단위 테스트 | **14 passed** |
| `/line` 엔드포인트 | 실측치 반환 — `detected=true` · offset −0.155 · conf 0.974 · **hz 24.8** · age 20.8 ms + `geom` |
| `/stream/<cam>` | HTTP 200 multipart, JPEG 패스스루 |
| 인덱스 페이지 | 정상 렌더 (`<title>AMR 라인 인식</title>`) |
| **방향 전환** | `POST /direction reverse` → `{"ok":true,"camera":"cam_r"}` · 인식 노드가 `cam_r` 로 전환 → 프레임이 없어 오차 나이가 3,019 ms 로 벌어짐(UI 「낡음」 처리) → `forward` 복귀 시 25 Hz 회복 |
| 오버레이 기하 | 브라우저와 같은 식으로 실프레임에 렌더해 대조 — 제어점이 테이프 위, 선이 테이프를 따라감 |

**시각 확인이 결함 1건을 찾았다(수정 완료)**: `angle` 은 픽셀 좌표계 기울기인데 정규화(0~1)
좌표로 옮기며 종횡비 보정을 빠뜨려, 16:9 화면에서 선이 **1.78배 가파르게** 그려졌다.
제어점에서만 맞고 위로 갈수록 라인에서 벌어진다. `centerline_points` 에 `aspect` 인자를
추가하고 노드 파라미터 `image_aspect` 로 배선했다. 수치만 봤으면 못 잡았을 형태다.

**브라우저 렌더링 — 사용자 확인(2026-08-14)**: 저자는 이 호스트에서 확인할 수 없었다
(firefox 가 snap 이라 헤드리스 캡처가 `snap-confine ... cap_dac_override not found` 로 막힌다).
사용자가 브라우저로 열어 「잘되네요」로 동작을 확인했다 — DOM·SVG 오버레이·스트림·수치판이
사람 관찰로 검증됐다. 위 기하 대조(OpenCV 렌더)는 그 보조 근거다.

**미검증**: 후방 카메라(`cam_r`) 표시 — **장치 미연결**이라 전환 경로만 확인했고 화면은 못 봤다.
주행 중 검출률도 별개다(위는 정지 상태 관측).
