# 2026-09-05 09:5x (KST) — 공유 작업트리의 낡은 파일을 세션 워크트리에 복사해 다른 세션의 기록 16줄을 지웠다

## 무엇을 했는가
09-04 커밋(9a152f3)에서 `docs/issues_and_fixes/issues_and_fixes.md` 를 공유 작업트리(브랜치 session/13ef822a, main 보다 뒤처짐)에서 세션 워크트리(origin/main 기준)로 `cp` 해 커밋했다.
공유 트리의 그 파일에는 main 에 이미 있던 「2026-09-02 [Fix] system_health GPU 사용률 표본 에일리어싱」 항목(다른 세션 작성)이 없었고, 그대로 main 에 병합돼 항목이 사라졌다.
15인 검토(deploy-vs-src 렌즈)가 "세션 브랜치 작업트리의 can_relay 가 main 보다 낡았다" 고 지적해 `git diff --numstat 5d09c55..07f8661` 로 삭제 줄을 점검하다 발견했고, 09-05 워크트리에서 원문을 복원했다.

## 무엇이 잘못이었나
- `docs/claude_guideline/git_workflow/git_workflow.md` §1 「명시 staging (세션 격리)」·§2-1 「격리 대상 = 이 세션의 산출물만」 — 다른 세션의 산출물을 (삭제라는 형태로) 내 커밋에 실었다.
- 세션 도구 안내(「그 폴더에서 작업하세요」)를 무시하고 공유 트리에서 편집한 뒤 복사했다. 공유 트리는 다른 세션 브랜치가 체크아웃돼 있어 main 보다 뒤처질 수 있다.

## 원인 분석
편집을 공유 트리에서 했기 때문에 "내가 고친 파일 = 복사하면 된다" 로 생각했고, 그 파일의 공유 트리 버전이 main 과 같은지 확인하지 않았다. 문서 파일(여러 세션이 prepend 하는 로그)은 특히 위험하다.

## 재발 방지
A류 후보 — 검출 규칙: 세션 워크트리 커밋 직전 `git diff --numstat origin/main -- <추적파일>` 에서 **삭제 줄이 있는 파일**을 모두 나열하고, 삭제된 블록이 이 세션 작성분이 아니면 차단(exit 1). 검출자는 다음 세션에서 번들 `detectors/2026-09-05-003.sh` 로 작성한다(본 세션은 실기·펌웨어 작업 중이라 미작성 — 사유 1줄).
절차 처방(즉시 적용): 세션 워크트리에는 **복사하지 않고 패치**한다 — 워크트리(main 기준)의 파일을 열어 같은 변경을 적용한다. 부득이 복사하려면 먼저 `git -C <공유트리> diff origin/main -- <파일>` 이 비어 있는지 확인한다. 공유 로그 파일(issues_and_fixes·registry·INDEX)은 항상 패치 방식.
