# 2026-07-29 06:08 (KST) — 호밍 정의를 안 보고 "④ 호밍 성공" 선언

## 무엇을 했는가

3계층 리팩터 후 실기 검증에서 GUI 가 출력한 로그 한 줄

```
[gui] 06:05:45  호밍 완료 — 31초 소요. 조향 0° 복귀까지 확인하세요.
```

을 근거로 사용자에게 **"④ 호밍 성공 — 31초 소요(문서 실측치와 일치). 완료 판정이
`미확인`이 아니라 `완료`로 났다는 건 … 판정이 새 계층 경계를 건너 제대로 동작했다는 뜻"**
이라고 보고했다. 호밍의 **정의**를 정본 기록과 대조하지 않았다.

## 무엇이 잘못이었나

- `docs/claude_guideline/coding/coding.md` §5 검증 — "검증 없이 완료·성공 선언" 금지.
  bit15 전이 관측은 **개시·완료 신호**의 검증일 뿐, "호밍이 정의대로 수행됐다"의 검증이 아니다.
- `docs/claude_guideline/external_reference/handling.md` — 1차 자료(실기 캡처 기록) 대조 없이
  **2차 산출물(우리 GUI 자신의 로그 문구)** 을 근거로 삼았다. 그 문구는 검증 대상이지 근거가 아니다.
- `CLAUDE.md` §코드 작성 SOP §2 사전조사 — 호밍 정본 기록
  (메모리 `biguamr-steer-homing-architecture`, `Log/homing_capture_220350.jsonl`)을
  **리팩터 착수 전에도, 실기 검증 보고 전에도** 읽지 않았다.

정본 캡처(`Log/homing_capture_220350.jsonl`, 253k 프레임)를 직접 파싱해 확인한 사실:

| t (s) | 사건 | node3 `0x6064` |
| --- | --- | --- |
| ~0–17.9 | 호밍 전, 직진 자세 | 7,871,818 → 7,882,014 (**+137.3°**) |
| 17.918 / 17.925 | `0x6099=2500` / `0x60FB:04=1` | |
| 17.956 | `0x6041` bit15 **1→0** | |
| 20–45 | 리밋 탐색 | **0 고정**(판독 정지) |

**호밍은 리밋까지 보내 드라이브 원점을 확립하는 절차이고, 끝나는 지점이 bit15 0→1 이다.**
그 시점에 바퀴는 리밋에 있다. 직진으로 돌아오는 137° 이동은 호밍의 단계가 아니라 **위치
지령에 의한 별개의 이동**이며, Seer 는 `0x607A` 를 노드당 6,464회(≈50 Hz)로 호밍 전·중·후
내내 끊김 없이 스트리밍하므로(값은 `7,871,815`↔`7,882,020` 2종뿐) 위치 루프가 알아서 되돌린다.

**우리 GUI 는 제어권 획득 후 유휴 상태에서 위치 목표를 물고 있지 않고 상태 읽기만 한다**
(`_loop` 는 `0x6064`·`0x606C`·`0x6078`·`0x6041` 읽기 전용 — 사용자 확인). 그러므로 호밍 뒤
**조향 0° 명령을 우리가 1회 보내야** 하는데, `_homing_run` 은 bit15 를 기다린 뒤 그대로
끝났다. 호밍 경로에 `0x607A` 가 0건이었다(리팩터 전 `88cd633` 도 동일 — 신규 결함 아님).
결과로 바퀴가 리밋에 얹힌 채 남고, 정본은 그 상태를 "리밋에 얹힌 채 두면 그 방향 지령이
막힌다"고 명시한다. 그런데 GUI 는 사용자에게 정반대로 안내했다:

| 화면·문서가 말한 것 | 코드가 하는 것 |
| --- | --- |
| 대화상자 "원점(리밋)으로 보낸 뒤 **0° 로 복귀시킵니다**" | 복귀 지령 미송신 |
| 완료 로그 "**조향 0° 복귀까지** 확인하세요" | 리밋에서 종료 |
| README "완료 후 바퀴가 크게 돈다 … 스윙 100° 초과" | 그건 **Seer** 위치 루프의 거동 |

## 원인 분석

규칙은 알고 있었고 세션 시작 훅이 `verify-skip` 메타 패턴을 **눈앞에 주입**하고 있었다
(2026-07-26-001 → 2026-07-27-002 → 2026-07-28-011 계보). 그럼에도 걸리지 않은 이유:

1. **리팩터라는 프레임이 검증 기준을 좁혔다.** 과제를 "값·순서를 보존했는가"로 놓으니
   구·신 프레임 대조(3,212 + 2,004 + 1,512건)까지 했으면서, 정작 **보존한 그 동작이 애초에
   옳은가**는 검사 범위 밖으로 밀렸다. 보존은 정확했다 — 틀린 것을 정확히 보존했다.
2. **완료 신호와 완료를 동일시했다.** 2026-07-28-011 의 "파일을 보고 장치를 말했다"와 같은
   형태다 — 이번엔 **프로그램의 자기 보고를 보고 로봇의 상태를 말했다.** 주장의 대상(로봇의
   조향 자세)과 검증의 대상(GUI 의 로그 문자열)이 달랐다.
3. 이관 문서 §4 가 "호밍 시퀀스는 값·순서 보존" 이라고만 적어 두어 **시퀀스가 완전하다는
   인상**을 줬다. 문서의 침묵을 완전성으로 읽었다.

## 재발 방지

- **회귀 테스트로 강제** — `test_homing.py` 에 5건 신설(88 → 93). 핵심은 **종료 상태를
  프레임으로 고정**하는 것이다: 완료 후 조향 2축에 `0x607A`(= `steer_counts(n, 0)`) +
  `0x6040=0x3F` 가 나가는가 / 그것이 `0x60FB` 트리거보다 뒤인가 / **원점 미확립 시에는
  나가지 않는가** / 판독 동결이 풀리는가 / `0x6098` 은 여전히 0건인가.
  기존 13건은 **개시 시퀀스만** 고정하고 종료를 보지 않아 이 결함을 통과시켰다 — 그 공백을 닫았다.
- **구현 수정** — `_homing_run` 이 bit15 확인 후 조향 0° 를 지령하고 정착까지 확인한다.
  판독 동결을 `homing`(인터록)에서 `_pos_frozen`(리밋 탐색 구간)으로 분리해, 복귀 이동이
  화면에 정상적으로 그려지면서도 그 동안 조그는 계속 막히도록 했다.
- **이름으로 고정** — 버튼·대화상자를 "**호밍 후 조향 0°**" 로 바꿨다(사용자 지시).
  "조향 원점 복귀 (호밍)" 은 호밍만 하고 끝나도 말이 되는 이름이라 결함을 가렸다.
- **실기 검증 보고 규칙** — 장비 동작을 "성공"으로 보고하기 전 그 동작의 정의를 **1차 기록
  (실기 캡처)에서 인용**하고 단계별 대조표를 만든다. 프로그램 자신의 완료 로그는 근거가 아니다.
- 리팩터 작업에서도 **착수 전 대상 도메인의 1차 기록**을 읽는다 — "위치만 옮기는 작업이라
  도메인 지식이 필요 없다"는 판단이 이번 공백의 입구였다.

> **정정**: 본 entry 최초 작성 시 호밍을 "리밋 탐색 → bit15 → 0° 복귀 지령의 3단계" 로,
> Seer 의 복귀를 "완료 직후 보내는 이산 지령" 으로 기술했다. 둘 다 틀렸다 — 사용자 지적
> 후 캡처를 직접 파싱해 위 표로 교체했다. 호밍은 bit15 에서 끝나며, Seer 의 `0x607A` 는
> 이산 지령이 아니라 상시 스트리밍이다.
