# 2026-08-07 18:16 (KST) — 원본 하드를 들고 있으면서 「벤더에 물어볼 목록」을 작성했다

## 무엇을 했는가

Seer TCP API 를 `src/Comm/TCP_IP/seer_api` 로 분리하면서 포트별 동시연결 한도를 정해야 했다.
동봉 PDF(protocol v1.2.1)는 지령 포트를 **1**, Feishu 최신(v1.4.2)은 **5** 라고 적고 있었고,
실기 컨트롤러가 신고한 `v3.4.5.22` 는 그 둘 중 어느 판본인지 알려주지 않았다.

여기서 나는 **「보수적으로 v1.2.1 값(1)을 채택」** 하고, 그 미확정을 debt-060 으로 등록한 뒤,
사용자에게 **벤더 문의 항목 7개를 복붙용으로 정리해 올렸다** — 프로토콜 판본, 포트별 최대
동시연결 수, 초과 시 거동, 레이트 제한, RoboShop 점유 포트, Push 구독 방법, 문서 PDF.
"2번(문서 PDF) 하나만 받아도 1·3·5·7 이 해결된다"는 조언까지 덧붙였다.

## 무엇이 잘못이었나

**답은 우리 손 안에 있었고, 물어볼 필요가 전혀 없었다.**

사용자 지적 후 `amap-server` 의 63G 원본 하드(Seer 루트파일시스템 사본)를 조회하자 30분 안에
전부 나왔다. 게다가 그 하드의 `rbk/product.version.h` 는 `PRODUCT_FULL_VERSION "3.4.5.22"` —
**실기와 동일 버전**이어서, 판본 대응표 없이도 그 자체가 정본이었다.

| 물어보려던 것 | 실제로 어디 있었나 |
|---|---|
| 포트별 최대 동시연결 수 | `robot.param`(SQLite) `NetProtocol` 테이블 — 19204·19301=**10**, 나머지=**5** |
| 초과 시 거동 | `libNetProtocol.so` 문자열 + 실기 실측 → **거부형**(기존 연결 생존), `ret_code 61001` |
| 프로토콜 판본 | **애초에 답이 없는 질문이었다** — 한도는 판본이 아니라 **런타임 파라미터**가 정한다 |

즉 내가 세운 문제 설정("판본을 알아야 한도를 안다") 자체가 틀렸다. 한도는
`Robot<카테고리>APITCPServerMaxConnections` 라는 **변경 가능한 설정값**이고(`minValue` 1,
`maxValue` 20, `advanced: true`), 심지어 **API 1400 으로 실기에 직접 물어볼 수 있었다** —
벤더도, 원본 하드도 없이, 이미 내가 짠 라이브러리로 한 줄이면 되는 일이었다.

그 결과 코드에 **틀린 상수**가 들어갔다. `MAX_CONNECTIONS_V121` 의 지령 포트 값 `1` 은 실제
`5` 와 5배 차이였고, 더 나쁜 것은 `EXCLUSIVE_PORTS` 를 그 값에서 **파생**시킨 것이다
(`n <= 1`). 값을 실측으로 고치는 순간 그 집합은 **빈 집합**이 되어 게이트 전체가 조용히
사라질 뻔했다. 틀린 사실 위에 강제 장치를 얹었던 셈이다.

## 사용자 지적

## 원인 분석

`context-missing` — 조사 후보 집합에서 **우리가 보유한 원자료**를 빠뜨렸다.

이 형태는 처음이 아니다. 같은 §메타 패턴에 이미 세 건이 있다:

- **2026-08-03-002** — 「`docs/` grep 에 없다 → 근거가 없다」. 저장소의 마스터 캡처를 안 봤다.
- **2026-08-05-001** — 「캡처에 없다 → 이 드라이브에 정지 명령이 없다」. 벤더 매뉴얼을 안 봤다.
- **2026-08-06-004** — 「저장소 grep 에 zmq 근거 없음」. **바로 이 63G 하드**를 안 봤다.

앞선 세 건과 이번의 차이는 **방향만 반대**라는 점이다. 이전에는 "문서에 없으니 없다"였고
이번에는 "문서에 애매하니 벤더에 묻자"였다. 공통점은 그대로다 — **원자료가 후보에 없었다.**
특히 `2026-08-06-004` 는 **같은 장비·같은 하드**였고, 그 사건 때문에 만들어진 접속 래퍼
`Tools/seer_re/amap_server.sh` 와 메모리 `biguamr-amap1-access`·`biguamr-seer-internal-transport`
가 이미 있었는데도 열지 않았다.

왜 안 열었나 — 정직하게 말하면 **주제를 "네트워크 API 사양"으로 분류했기 때문**이다. 그 하드는
내 머릿속에서 "리버스 엔지니어링 자산(libMCLoc·측위)" 으로 태그돼 있었고, "API 포트 설정" 은
그 태그에 걸리지 않았다. 자산은 있었고 접근법도 문서화돼 있었으나 **검색 키가 어긋났다.**
「원본을 보라」는 지시를 또 적는 것으로는 이 어긋남이 닫히지 않는다 — 이전 세 번이 그 증거다.

## 재발 방지

**「읽어라」를 또 적지 않는다.** 이번에 닫은 방법은 셋:

1. **실행 가능한 조회기를 만들었다** — `Tools/seer_re/seer_param.sh`.
   robot.param(원본 하드)과 실기 API 1400 을 **양쪽 다** 조회해 값을 나란히 찍는다.
   "물어볼까?" 대신 이 스크립트를 돌리면 30초에 답이 나온다. 하드 경로·계정·타임아웃은
   기존 `amap_server.sh` 를 재사용하므로 이름이 바뀌어도 한 곳만 고친다.
2. **코드가 상수를 진실로 주장하지 않게 바꿨다** — `ports.OBSERVED_MAX_CONNECTIONS` 는
   docstring 에서 스스로 "정본이 아니라 관측 기본값" 이라고 선언하고,
   판정이 필요하면 `SeerApi.get_max_connections()` 가 **로봇에 직접 묻는다**(API 1400).
   상수가 틀려도 판정 경로는 안 틀린다. 돌연변이 `A13` 이 이 우회를 막는다.
3. **파생 게이트를 명시 게이트로 바꿨다** — 사실이 뒤집혔을 때 강제 장치가 조용히 사라지는
   구조를 없앴다. `GUARDED_PORTS` 는 명시 집합이고, 한도에서 파생하는 변조는 돌연변이 `P2`
   가 잡는다. 게이트의 근거도 "동시연결 1"(반증됨) → "지령 중재"(반증 불가)로 바꿨다.

부수 기록: debt-060 은 「판본 미확정」 부분이 **해소**되어 「broker 미착수」만 남았다.
