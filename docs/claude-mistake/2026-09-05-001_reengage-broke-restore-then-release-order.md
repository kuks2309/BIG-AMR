# 2026-09-05 09:04 (KST) — 재engage 처리가 "복원 완료 → 제어권 해제" 순서를 깰 수 있게 구현했다

## 무엇을 했는가
09-04 핸드오버 복원 시퀀서에 "복원 중 재engage 가 오면 완료 후 권한 유지" 를 넣으면서, 재engage 뒤에 다시 반환 요청이 오는 경우를 다루지 않았다.
`seer_handover_request()` 는 진행 중이면 조기 반환해 `seer_ho_reengage` 가 남고, finish 가 그 플래그를 보고 권한을 유지해 호스트 없이 intercept 가 고착될 수 있었다.
15인 검토(backend-shutdown·reengage-race 렌즈)가 지적했고 사용자가 "반환 시 스티어링 복구 후 제어권 해제 순서" 를 재확인하며 바로잡았다.

## 무엇이 잘못이었나
- 사용자 요구(09-04 21:1x, 09-05 09:04)의 불변식 "반환 요청은 반드시 복원 완료 → 권한 해제 로 끝난다" 를 상태기에 새기지 않았다.
- `coding.md` §3 사전승인·§5 검증: 상태기 전이표(요청 순서 × 상태) 없이 구현했고, 재engage 뒤 재반환 순서를 시험하지 않았다.

## 원인 분석
재engage 를 "한 번 오는 이벤트" 로만 생각했고, 그 뒤에 올 수 있는 반환 요청과의 결합을 열거하지 않았다. 검증도 단일 순서만 돌렸다.

## 재발 방지
B류. `mistake-relevance` 가 `safety_seer_gate.h`·`usb_comms.h` 편집 시 본 사건을 낸다(토큰 `seer_ho_reengage`·`seer_handover_request`).
처방: 상태기에 플래그를 추가할 때 (요청 종류 × 현재 상태) 전이표를 먼저 적고, "최신 요청이 이긴다" 같은 규칙으로 잔류 플래그를 없앤다. 실기 검증은 요청 2연속·3연속 순서를 포함한다(ADR 09-05 절 표).
