# 2026-07-28 17:45 (KST) — 장치 상태를 조회 없이 배포 파일 md5 로 확정

## 무엇을 했는가

CAN Relay firmware 코드 리뷰에서 High 결함 하나를 다음과 같이 확정 보고했다.

> "현장 배포 펌웨어가 소스보다 한 세대 뒤 … **호밍 시퀀서(0xea/0xeb)·0xec·차량 safety 모드 제거는 소스에만 존재하고 실기에 플래시된 적이 없다.** `orin_homing_run.py` 를 현 실기에 대고 돌리면 `0xea` 는 미정의 요청이다."

근거로 삼은 것은 저장소 밖 배포 경로 `~/Project/CAN-Relay/docking_field_kit/panda.bin.signed` 의 서명 md5 가 백업 `fw_backups/panda.bin.signed.pre_homing_2026-07-27` 과 같다는 사실뿐이었다. **판다 장치 자체는 한 번도 조회하지 않았다.**

이후 사용자가 "문서로만 하지말고 없을 경우에는 실제 구동을 해 보면 됨" 이라고 지시해 읽기 전용 USB 조회(`0xd3`+`0xd4` 서명 판독)를 실행한 결과, 실기 서명 md5 는 `b31d67899631bdf30483a12a6ced7b4e` 로 **현재 빌드 `board/obj/panda.bin.signed`(30,268 B)와 완전 일치**했다. 즉 호밍 시퀀서는 실기에 이미 올라가 있었고, 보고는 사실과 반대였다.

## 무엇이 잘못이었나

- `docs/claude_guideline/reverse_engineering/principle.md` §6 분석 보고 원칙 — `[존재]`(nm/disasm) vs `[동작]`(호출 도달성 + **배포자산 대조**) 라벨 분리, **동작 주장은 배포자산 대조 전 "확정" 금지**.
- 루트 `CLAUDE.md` 리버스 엔지니어링 등록 절 — 동일 규칙을 세션 진입 시 재확인하도록 지시.
- 가중 사유: **같은 리뷰 문서의 다른 항목(H3)에서 내가 직접 이 규칙을 인용해 `[존재]`/`[동작]` 라벨을 분리해 놓고**, 정작 그 항목 본문에서는 장치 미조회 상태로 `[동작]`을 확정했다.

## 사용자 지적

> "문서로만 하지말고 없을 경우에는 실제 구동을 해 보면 됨"

문서·파일 대조로 판정을 끝내지 말고, 근거가 없으면 실제로 돌려서 확인하라는 교정. 이 지시를 따라 조회한 즉시 보고가 뒤집혔다.

## 원인 분석

규칙 가시성·강제력 점검:

- **규칙을 알고 있었나** — 알고 있었다. 같은 문서에서 인용까지 했다. 지식 공백이 아니다.
- **세션 시작 시 주입되었나** — 주입됐다. `CLAUDE.md` 의 reverse_engineering 등록 절이 세션 컨텍스트에 있었다.
- **가이드라인이 모호했나** — 모호하지 않다. "배포자산 대조 전 확정 금지"는 명시적이다.
- **hook 이 부재였나** — 부재했다. 이 저장소에는 `checks/` · pre-commit · CI 가 모두 미설치(`CLAUDE.md` 최상단 고지)이므로 `[동작]` 확정을 차단할 기계가 없다.
- **실질 유인** — 배포 경로 파일과 백업 파일의 md5 가 일치하자 그것을 "배포자산 대조"로 착각했다. **배포 *스테이징 파일*은 배포자산이지만 *장치 상태*가 아니다.** 두 개념을 구분하는 서술이 규칙에도 내 절차에도 없었고, 판다가 USB 로 연결돼 조회가 수 초면 끝난다는 사실을 확인조차 하지 않았다.

## 재발 방지

- **[반영 완료]** 리뷰 산출물에 `## 실기 실측 부록` 신설 — 읽기 전용 vendor request 만으로 장치 상태를 확정하는 절차(`0xd6` 버전 / `0xd3`+`0xd4` 서명 md5 / `0xd2` health / `0xc3` can_health)와 실행 방법을 기록했다. 호스트 라이브러리 `Panda()` 생성자가 `0xf8`(heartbeat 검사 해제)을 보낼 수 있으므로 **우회하고 `usb1` 로 직접 control read** 하라는 주의도 함께 명시.
- **[반영 완료]** 같은 문서의 해당 High 항목을 정정하고, 정정 사유("파일 md5 만 보고 장치 상태를 추정 — reverse_engineering SOP §6 을 작성자 스스로 위반")를 항목 본문에 남겼다.
- **[반영 완료]** `docs/claude_guideline/code_review/checks/review-claim-lint.py` 에 **S5 규칙** 구현 — findings 블록 안에 `[동작]` 라벨이 있으면 같은 블록에 배포자산 대조 근거가 있어야 하고, 없으면 FAIL 한다. 인정 근거는 두 종류로 한정했다: ① 장치 직접 조회(`0xd2`/`0xd3`/`0xd4`/`0xd6`/`0xc3`/`get_signature`/실기 조회) ② 실기 캡처 로그 재집계(`Log/*.jsonl`·캡처 재집계). **문서·소스 인용만으로는 통과하지 못한다** — 이 사건의 실패 형태가 정확히 그것이었기 때문이다.
- **[반영 완료]** 회귀 시험 — 이 사건을 합성한 케이스("배포 경로 파일 md5 가 백업과 동일" 근거만으로 `[동작]` 확정)에서 S5 가 FAIL 하고, 캡처 로그 근거를 가진 정상 항목은 통과함을 확인했다. 정정된 정본은 S1~S5 전항 PASS.
