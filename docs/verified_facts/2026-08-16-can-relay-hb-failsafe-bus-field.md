# can_relay — 심박 상실 시 펌웨어 fail-safe 의 버스 수준 직접 관측 (2026-08-16)

## 목적

심박(0xf3) 상실 시 펌웨어가 실제로 ① 구동 정지(0x60FF=0)를 버스에 쓰고 ② 릴레이를
여는지(Seer 통과)를 **버스 프레임으로** 확인한다 — 지금까지의 모든 실험이 남겨 둔
마지막 미확정(debt-075 잔여)이다.

## 방법 — 판다 자체가 계측기

판다는 양쪽 버스에서 수신한 전 프레임을 호스트로 올리므로 별도 캡처 장비가 불필요하다.
도구: `Tools/can_relay_field/hb_failsafe_capture.py` (판다 단독, ROS 불요) —
`PandaLink.open→acquire`(드라이버와 동일 경로) → 기준 5 s(심박 0.2 s 주기) →
**심박만 중단** 15 s(수신은 계속) → `release→close`. 구동·조향 지령 0건.
실행 전 드라이버 노드가 미획득 대기(USB 미개방)임을 확인했다.

## 조건

## 관측

심박 중단 시각 t=5.01 s (이하 상대 시각).

### ① 펌웨어 정지 쓰기 — 직접 증거

중단 **+1.60 s**(임계 1~2 s 정합)부터 드라이브측(bus2) 수신에
`0x581`·`0x582`(구동 노드 1·2 의 SDO(Service Data Object) 응답) =
`60 ff 60 00 00 00 00 00` — **index 0x60FF(목표속도) download ACK** 가 연발했다
(115 ms 에 12건+). 이 구간에 호스트는 아무 프레임도 보내지 않았으므로 그 쓰기의
주체는 펌웨어뿐이다 — `seer_stop_drives`(0x60FF=0 반복 쓰기)의 실행이 드라이브
응답으로 실증됐다.

### ② 릴레이 개방 — 트래픽 개시

| 지표 | 기준(심박 정상) | 심박 중단 후 |
| --- | --- | --- |
| bus2(드라이브측) 수신율 | 922.8 /s | **1484.5 /s** |
| bus0(Seer측) 수신율 | (기준 상단 0x601~0x604 각 200~257 /s) | 1516.4 /s |

중단 직후 bus2 에 노드 3·4 하트비트(`0x703`·`0x704`)를 포함한 전 노드 응답
스트림이 개시·증대 — Seer 요청이 드라이브에 전면 도달하기 시작한 것과 정합한다.

### 부수 관측 — intercept 중에도 Seer 폴링은 릴레이된다

기준 구간(intercept)에도 bus2 에 드라이브 응답이 상당량(≈920 /s) 존재했다 —
intercept 는 Seer 를 완전 차단하는 것이 아니라 폴링류를 중계한다는 기존 실증
(emulate 실위치 릴레이, 2026-08 55602 관측)과 정합한다. echo 버스(bus128/130,
판다 자신이 송신한 프레임의 루프백)도 같은 그림을 보인다.

## 판정

| 주장 | 판정 |
| --- | --- |
| 심박 상실 → 펌웨어가 0x60FF=0 을 드라이브에 쓴다 | **실기 확정** (드라이브 ACK 직접 관측, +1.6 s) |
| 심박 상실 → 릴레이 개방(Seer 통과 개시) | **실기 확정** (bus2 트래픽 개시·수신율 +61 %) |
| 발동 시점이 점화 off 임계(1~2 s)와 일치 | **실기 확정** (+1.60 s) |

## 관측의 한정

- 점화 off 조건만 시험했다(임계 1~2 s). 점화 on(4~5 s) 임계는 미시험.
- ACK 는 쓰기 성공의 증거이며 쓰기 프레임 자체(0x601/0x602 송신)는 펌웨어 발신이라
  호스트 수신에 나타나지 않는다 — 주체 귀속은 「그 구간 호스트 송신 0건」으로 확정.
- echo 버스 번호(128/130 = 0x80|bus) 해석은 판다 관례 기반이며 판정에는 쓰지 않았다.
