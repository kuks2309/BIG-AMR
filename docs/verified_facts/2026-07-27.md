### A-1. 판다 부팅 기본 CAN 비트레이트가 500 kbps 여서 250 kbps 버스를 파괴하고 있었다

**증상 관측** — 로봇 전원 인가 후 호스트 소프트웨어를 **하나도 실행하지 않은 상태**에서 Seer API 1050 폴링:

```
errors   52106 odo data lost
errors   52111 motor driver connection error
warnings 54022 CAN1 new error:0x40, count:136, Bit Recessive error
warnings 54301 Motor is calibrating
```

`54022` 타임스탬프가 **10 초마다 갱신**(20:09:20 → :30 → :40 → :50, 코드 0x40/0x50 교대)
→ 일회성 트랜지언트가 아니라 **진행 중**.

**개입(단일 변수)** — `set_can_speed_kbps(0, 250)`, `set_can_speed_kbps(2, 250)` **만** 수행.
safety_mode 무변경(0 유지) · `0xe8`(intercept) 미설정 · `0xe9`(auth) 미설정 · 모터 지령 0 건.

**결과**

```
[t+18s] errors=[]  54022=(없음)
[t+24s] errors=[]  54022=(없음)
[t+30s] errors=[]  54022=(없음)
```

**결론**: 원인은 비트레이트 불일치. 판다가 250 kbps 버스에 500 kbps 로 붙어 전 프레임을 오독하고
에러 프레임을 방출하고 있었다.

**코드 근거**
- `Tools/Can_Relay/panda-firmware/board/drivers/can_common.h:164-166` — `bus_config[].can_speed = 5000U`
- 단위: `board/usb_comms.h:322` 가 `wIndex` 를 그대로 저장 + `Tools/docking_field_kit/panda/python/__init__.py:550`
  이 `int(speed*10)` 송신 ⇒ `5000U` = **500 kbps**

**왜 지금까지 안 드러났나**: 모든 호스트 도구가 제어권 획득 시퀀스에서 `set_can_speed_kbps(b, 250)` 을
호출한다(`docking_field_kit/docking_drive.py:75-76`, `Tools/amr_test_gui/amr_test_gui/panda_can_bus.py::_take`).
즉 **PC 소프트웨어가 붙어야만 버스가 성립**하는 구조였다.

**수정 후 재검증** — `can_speed` → `2500U` 로 고쳐 빌드·플래시한 뒤, **비트레이트를 아무도 설정하지 않은
상태**에서:

```
[판다] safety_mode=0 harness=1 uptime=42s rx_errs=0 faults=0
8초간 수신 프레임 = 29,625        ← 부팅 기본값이 250 kbps 임을 기능으로 입증
[Seer] t+00s errors=[]  t+07s errors=[]  t+14s errors=[]  t+21s errors=[]
```

운전자 육안 확인: "오류 안남".

**재현**: 판다 전원 재인가 → 호스트 SW 미실행 → `python3 Tools/docking_field_kit/seer_can_monitor.py 192.168.44.82`

### A-2. Seer 가 실제로 폴하는 SDO 인덱스 집합

**절차**: 비트레이트 정합 후 12 초간 판다 RX 를 읽어 bus0 의 `0x601~0x604`, cmd `0x40`(read) 프레임의
인덱스를 집계. 제어권 미획득 상태(읽기 전용).

**원시 데이터** (12 초)

| index | 폴 횟수 | 비고 |
| --- | --- | --- |
| `0x6064` 위치 | node1 2920 · node2 2908 · node3 2720 · node4 2718 | 압도적 다수 |
| `0x6041` statusword | node3 312 · node4 301 · node1 66 · node2 66 | 조향축에서 특히 많음 |
| `0x603F` error code | 각 노드 68 | |
| `0x6078` 전류 | 각 노드 66 | |
| `0x6000` sub=1 digital in | 각 노드 66~68 | |
| **`0x606C` 실속도** | **0** | **Seer 는 폴하지 않는다** |

### A-3. 릴레이는 부팅 시 버스를 **물리적으로 연결**한다 (펌웨어 포워딩 무관)

**코드 근거**: `board/drivers/harness.h:91`

```c

```

**실측 뒷받침**
- `health()` → `car_harness_status = 1` (HARNESS_STATUS_NORMAL — 하네스 감지됨)
- 같은 프레임이 bus0 과 bus2 에 **동일 카운트**로 잡힘: `0x603` → bus0 2615 / bus2 2615,

> 은 사실이나, 릴레이가 물리 통과이므로 그 경로는 애초에 필요가 없었다.

### A-4. `can_send_errs` 는 송신 오류가 아니라 **USB RX 큐 오버플로 드롭** 카운터다

### A-5. heartbeat 상실 시 펌웨어는 `SAFETY_SILENT` 로 복귀한다 (passthrough 아님)

**코드 근거**: `board/main.c` heartbeat 블록

```c
if (current_safety_mode != SAFETY_SILENT) { set_safety_mode(SAFETY_SILENT, 0U); }
if (power_save_status != POWER_SAVE_STATUS_ENABLED) { set_power_save_state(POWER_SAVE_STATUS_ENABLED); }
```

**실측 정합**: 호스트 미접속 상태의 판다 health → `safety_mode=0`, `power_save_enabled=1`.

**결론**: 여러 문서·주석에 있던 "heartbeat 소실 시 fail-safe **passthrough** 복귀"는 **부정확**하다.

이상 상태에서 릴레이가 intercept 로 남지 않게 했다(사용자 요구).

### A-6. GUI Space 키 E-STOP 이 포커스에 따라 **반대로** 동작했다

**절차**: `QTest.keyClick` 로 포커스별 재현(offscreen).

**원시 데이터 (수정 전)**

```
모드버튼(전진) 포커스 + Space → E-STOP=False,  전진버튼 재클릭 1회
E-STOP 체결 상태 + E-STOP버튼 포커스 + Space → checked=False, controller._estop=False (해제됨)
```

**수정 후 재측정**: `모드버튼 포커스+Space → E-STOP=True, 재클릭 0회` / `체결 상태에서 Space → 유지`

### A-7. 피드백 staleness 미검사로 램프의 피드백-소실 FAULT 경로가 도달 불가였다

**절차**: 주행 중(SETTLED, raw −1222) `bus.recv` 를 영구 `None` 으로 만들어 RX 사망 주입.

**원시 데이터**
- 수정 전(게이트 무력화 재현): RX 사망 **7 초 후에도** `state=SETTLED · raw=-1222 · drive_ok=True`
- 수정 후: RX 사망 4.6 초 후 `state=FAULT · raw=0 · drive_ok=False`, 사유 "조향 피드백 미수신(4s)"

**결론**: `backend._nodes[n].pos` 는 브링업 이후 `None` 으로 되돌아가는 경로가 없으므로,
`last_seen` 신선도 검사 없이는 낡은 값으로 계속 주행한다.

**③ 결론 (5회 재현이 일치한 것만)**

1. **호밍은 CiA402 표준 호밍이 아니다.** 트리거는 벤더 오브젝트 **`0x60FB:04 = 1` 단 1회**이고,
   `0x6060`이 6(Homing mode)으로 설정된 적도 `0x6040`에 `0x800F`가 쓰인 적도 없다.
   호밍 속도도 표준 `0x6099:01/:02`가 아니라 **`0x6099:00` 단일값**(2500 = 250.0 r/min)으로 준다.
2. **`0x6064 ≈ 0` 은 「조향이 홈에 있다」의 지문이 아니라 「호밍 진행 중」의 지문이다.**
   정확히 0 인 구간은 `[17.930, 49.178]` 하나뿐이고(노드당 3,115 샘플, 전부 값 0),
   그 구간은 statusword bit15 = 0 구간과 겹친다. 그 밖에서는 **바퀴가 직진이어도** 약 7.88 M / 7.86 M 이다.
3. **호밍은 기존 원점을 재현했다.** 호밍 **전** 7,882,014 / 7,859,058 → 호밍 **후** 7,882,008 / 7,859,065,
   차이 **−6 / +7 counts (≈0.0001°)**.
4. **`config` 홈 상수와 호밍 후 복귀 목표는 같은 값이 아니다.** `0x607A` 구간 1·3 은
   `7,871,815 / 7,840,086`(= `steer_home_counts` 와 counts 단위 완전 일치)인데,
   호밍 후 구간 4 는 **`7,882,020 / 7,859,062`**다. 차이 **+10,205 / +18,976 counts (+0.178° / +0.331°)**.
5. **지령 측에는 137° 규모의 어긋남이 전혀 없다.** `0x607A` 값은 전부 7.87 M 대이며
   `config` 홈에서 벗어난 최대폭이 18,976 counts(0.331°)다.
6. **조향 지령은 단계로 쪼개지지 않는다 — 최종 절대 목표를 반복 송신한다.**
   노드당 `0x607A` 6,464 프레임에 **서로 다른 값은 2 개뿐**이고, 실제 이동이 일어난
   호밍 구간(t=17.88~49.14)에는 `0x607A` write 가 **0 프레임**이다. 즉 이동 프로파일은
   드라이브가 자체 수행한다(`0x6081` ProfileVelocity·`0x6083` Acc·`0x6084` Dec, 기동 시 1 회 설정).
   ⇒ **"조향을 N° 단계로 나눠 보내고 단계마다 정착을 확인한다"는 이 시스템의 지령 방식이 아니다.**
   그런 절차가 필요하다면 그것은 **사용자가 지정한 시험 절차**이지 시스템 요구가 아니므로,
   둘을 구분해 인용할 것(경위: `docs/claude-mistake/2026-07-28-003`).

>     **판정에 필요한 측정**: 조향 4 노드에 `0x6098:00` SDO upload 를 걸고 응답 프레임을 raw 로 기록.

>     캡처 밖에 있으므로 게이트는 **그대로 유지**한다.

>   기원이 `2026-07-27-002` 사고의 **원인**이라는 인과는 여전히 확인되지 않았다(판정 변화 없음).
