- 대상: Orbbec Gemini E RGB 6대 (1280x720 MJPG 30fps) + `usb_cam_publisher` 6노드 + `vision_guard` 뷰어(2x3)
- 기간: **2026-07-27 18:48:52 → 2026-07-28 03:15:21 (8시간 26분, 목표 24시간의 35%)**
- 중단 사유: **배터리 방전에 의한 전원 상실** (테스트 대상 결함 아님)
- 원시 자료: `Log/usb_cctv_soak_2026-07-27/` — `pub.log`(캡처 보고 36,390건), `viewer.log`(표시 보고 506건), `soak_samples.csv`(1,013행)
- 분석 도구: `Tools/usb_cam_bench/soak_stats.py` (단위 테스트 12 passed)

## 2. 상세

### P1. 전원 상실 (HIGH)

- 마지막 표본 `2026-07-28T03:15:21`(경과 8.4413h) 이후 기록 없음. 로그 말미가 잘린 형태로, 정상 종료 흔적(`process has finished cleanly`)이 없다 → 급작 전원 차단.
- 재부팅 08:11(수동 전원 인가). 약 5시간 정지.
- **테스트 대상 결함이 아니다.** 다만 24시간 무중단 증거는 확보하지 못했다.

### P2. 캡처 FPS 저하 군집 (MEDIUM, 원인 미확정)

- 25fps 미만 보고 **83건 / 36,390건 = 0.23%**. grab_failures 는 전 구간 **0** (프레임 유실 없음, 지연만 발생).
- 시간 분포가 균일하지 않고 **22:10~23:10 과 00:00~00:10 에 집중**(12개 10분 버킷에만 발생):

  | 구간 | 건수 |
  | --- | --- |
  | 22:10 | 39 |
  | 23:00 | 12 |
  | 22:50 / 00:10 | 6 / 6 |
  | 나머지 8구간 | 각 1~5 |

- **6대가 동시에 저하한 창이 존재**(22:15:20 / 22:15:30 / 22:15:40 에 cam0~cam5 전부). 최저값도 이 구간(22:15:39 cam2 **7.91fps**).
- 카메라별·버스별이 아니라 **호스트 공통 원인**을 가리킨다. 같은 시간대 퍼블리셔 CPU 합이 평시 152~158% → **최대 230%** 로 상승했다.
- 상관 후보(확정 아님): 다른 세션이 22:29 저장소 재배치, 22:32·23:16 `colcon build`, 22:33 테스트를 수행한 기록이 있다(`log/build_2026-07-27_22-32-07`, `_22-32-21`, `_23-16-51`, `log/test_2026-07-27_22-33-10`). 다만 **최대 저하 시각(22:15)은 이 빌드들보다 앞서** 단독으로는 설명되지 않는다.
- 열 throttle 여부는 **확인 불가**(P5).

> 판정: 저하는 재현·규명되지 않았다. 원인을 특정하지 않고 "미확정" 으로 남긴다.

### P3. 표시 렌더율 72% 와 FPS 표기 왜곡 (MEDIUM)

- 카메라별 누적 렌더: 639,148 ~ 649,422 프레임 / 8.42시간 → **실측 평균 21.1~21.4 fps**.
- 같은 구간 캡처는 29.6fps → **렌더율 약 72%**. 나머지 28%는 `LatestFrameStore` 설계상 드롭(메모리 상한 유지 목적)이므로 결함은 아니다.
- 그러나 화면·로그의 FPS 표기는 **25.7~25.9** 로 실측보다 약 4fps 높다. 표기값이 지수이동평균(EMA)이라 순간 고속 구간에 치우친다 → **표기값을 성능 근거로 쓰면 과대평가**한다.
- 최악 1분에도 898~909 프레임(약 15fps)은 유지, **정지(0장) 구간 0건** — 뷰어 자체 경고 0건과 일치.

### P4. 관측 도구의 정지 판정 오류 (MEDIUM, 수정 완료)

- 뷰어는 보고 구간의 **증분** 프레임 수를 찍는데 분석 코드가 **누적**으로 간주해 한 번 더 차분, "두 구간 값이 같음"을 정지로 오판했다. 초기 보고 "정지 4~8건"은 **오보**이며 실제 0건이다.
- 조치: 반환 키 `frames` → `frames_delta` 개명(오독 시 즉시 실패), 정지 판정을 `== 0` 으로 교체, `min_frames_delta` 추가, 회귀 테스트 `test_summarize_display_equal_deltas_are_not_stalls` 추가. 사건 기록 `docs/claude-mistake/2026-07-28-001_soak-stall-count-misread.md`.

### P5. 관측 공백 (MEDIUM)

수집하지 않아 P2 를 규명할 수 없었던 항목:

- 시스템 전역 CPU·loadavg (프로세스별만 수집)
- SoC 온도·throttle 이벤트 (`/sys/devices/virtual/thermal/`, `tegrastats`)
- USB 컨트롤러 에러 카운터·`dmesg` USB 이벤트
- 디스크 여유·I/O 대기

추가로 이전 부팅의 journal 이 보존되지 않아(볼륨 휘발) 사후 확인도 불가능했다.

### P6. 표본 주기 불일치 (LOW)

모니터 30초 / 뷰어 보고 60초 → CSV 표시 관련 열의 **절반이 공란**(1,013행 중 표시값 506행). 분석 시 필터가 필요하고 오해 소지가 있다.

### P7. RTC 미동작 (LOW)

부팅 직후 커널 시계가 `2026-06-06 00:40` 로 시작해 `systemd-timesyncd` 가 기록 시각(02:54:01)으로 복원, **08:11:04 NTP 동기**로 실제 시각 확보. 재부팅 직후 생성되는 로그의 시각은 신뢰할 수 없다(이번 분석에서는 중단 전 로그만 사용해 영향 없음).

### P8. 중단 시 요약 미생성 (LOW)

`soak_monitor.py` 는 24시간 완주 후에만 `soak_report.md` 를 쓴다. 이번처럼 중단되면 요약이 없어 수동 재분석이 필요했다.

## 3. 정상 확인된 사항 (8.44시간 근거)

- **메모리 누수 없음** — 뷰어 RSS 213.8 → 213.0 MB (최대 264.4 @ 21:56, 증가 **-0.8MB**). 과거 5대 구성의 OOM(1시간 11GB) 재발 없음.
- **프로세스 사망 0회** — 뷰어 1개·퍼블리셔 6개가 전 1,013 표본에서 생존.
- **프레임 유실 0** — grab_failures 전 카메라 0.
- **에러 로그 0건** — `pub.log`·`viewer.log` 의 ERROR/WARN 0.
- **CPU 여유** — 뷰어 136% + 퍼블리셔 148% = 평균 **284% / 800%**(8코어), 최대 340%.
- FastDDS 공유메모리 세그먼트 30~37 사이에서 등락, 단조 증가 없음(누수 아님).

## 4. 다음 실행 전 권고

1. **전원 확보** — 24시간 완주에는 상시 전원 필요(배터리 구동 불가). P1 재발 시 다시 부분 데이터만 남는다.
2. **모니터에 전역 지표 추가**(P5) — 총 CPU·loadavg·SoC 온도·throttle 카운터·USB 에러. P2 재현 시 원인 규명 가능.
3. **중단 시에도 요약 생성**(P8) — SIGTERM 핸들러 또는 N분마다 중간 요약 갱신.
4. **표본 주기 정합**(P6) — 모니터 60초 또는 뷰어 보고 30초로 통일.
5. **성능 근거는 실측 렌더율 사용**(P3) — 화면 표기 EMA FPS 대신 `total_frames / elapsed`.
