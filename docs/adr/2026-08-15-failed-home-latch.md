# ADR 2026-08-15 — 실패한 호밍 뒤에는 드라이브의 bit15 를 조향 허용 근거로 쓰지 않는다

- **Status**: Accepted — 2026-08-15 (⚠ **실기 미검증** — 단위·회귀 + 돌연변이 확인만.
  실기 재현은 호밍을 일부러 실패시켜야 하므로 다음 이동구역 확보 시점에 확인)

> 약어: ADR(Architecture Decision Record) · GUI(Graphical User Interface) ·
> DI(Digital Input) · SDO(Service Data Object)

## Context

`RelayBackend.homed_effective()` 는 조향 지령을 열지 말지를 정하는 단 하나의 게이트이고,
조향 경로 3곳이 전부 이것을 쓴다(`set_steer_deg` · `set_steer_axis_deg` · `set_motor_cmds`).
인정 근거는 둘이다 — ① 우리가 호밍했다(`_homed`) ② 드라이브가 `0x6041` bit15 로 완료를
보고한다. ②는 **Seer 가 호밍한 경우를 인정하려고** 2026-08-04 에 일부러 넣은 것이다
(그 전에는 우리 프로세스 변수만 봐서, Seer 호밍 상태인데 바퀴가 한 카운트도 안 움직였다).

**그런데 bit15 는 「원점을 잡았다」이지 「0° 에 서 있다」가 아니다.** 호밍 시퀀스는
원점(리밋) 탐색 → 0° 복귀(GOZERO) 두 단계인데, 뒷단계가 실패해도 bit15 는 1 로 남는다.

2026-08-14 17시 실기가 정확히 그 조합이었다:

```
호밍 결과  ERR_GOZERO (reached_mask=0x01)     ← 실패. node3 만 도달
node3      sw=37968(0x9450) → bit15=1
node4      sw=37968(0x9450) → bit15=1  pos=0  DI=9(−리밋)
```

`pos=0` 은 시퀀서 경로에서 **비정상**이다 — 정상 완주 시 축은 GOZERO 목표
(`7,882,020 / 7,859,062`)에 서 있어야 한다. node4 는 리밋에 그대로 있었다.

드라이버는 이 상태를 정직하게 보고한다 — `HOMING_OK = frozenset({5})`(DONE 만 성공,
`link.py:78`)이므로 `home()` 은 `(False, "ERR_GOZERO …")` 를 반환하고 `_homed=False` 로 둔다.
**문제는 그 다음이다**: `homed_effective()` 가 ②를 근거로 True 를 돌려주므로, 호출부가
실패 응답을 무시하고 조향 0° 를 지령하면 **게이트를 그대로 통과한다.** 축이 어디 서 있는지
모르는 채 지령이 나가고, node4 는 리밋에서 0° 까지 ≈136.7° 를 움직이게 된다.

지금 그 사고를 내는 코드 경로는 없다 — `~/home` 을 부르는 유일한 곳(통합 GUI 의 ROS2 탭,
`ui/backend_ros2.py:319`)은 0° 를 쏘지 않는다. 다만 ADR 2026-08-08 §Decision 2 가 정한
드라이버 쪽 `steer_to_zero()` 가 **미구현**이고, 그것이 쓰이는 순간 이 경로가 열린다.

## Decision

**우리가 건 호밍이 끝을 못 봤으면 그 뒤로 ②(드라이브 bit15)를 인정하지 않는다.**

1. 인스턴스 상태 `_home_failed` 를 둔다 — 「축을 움직여 놓고 성공으로 끝내지 못했다」.
2. **축이 실제로 움직이기 시작하는 지점**에서 세운다(비관 기본값):
   `home()` 은 펌웨어가 시퀀스를 수리한 직후, `_home_method35()` 는 이동 프레임 송신 직전.
   그래서 프로세스가 중간에 죽어도 래치는 서 있는 쪽으로 남는다.
3. **성공한 완주만 푼다** — `home()` 의 terminal 상태가 `HOMING_OK` 일 때, `_home_method35()`
   가 재영점을 확인했을 때.
4. `homed_effective()` 는 `_homed` 다음, 피드백 검사 **앞**에서 `_home_failed` 를 본다.
   ①(우리 호밍 성공)이 우선이므로 성공 직후 래치가 남아 스스로를 막는 일은 없다.
5. 거부 사유(`_not_homed_reason()`)는 이 경우 **노드별 bit15 를 나열하지 않는다** —
   전부 1 로 보이는 것이 정확히 래치가 있는 이유라, 나열하면 오해만 키운다.
6. raw 경로(`set_motor_cmds`)의 거부 note 에도 같은 사유를 싣는다. 종전에는
   `"node3 호밍 미완료 — 조향 거부"` 뿐이라 상위 모션이 원인을 구분할 수 없었다.
7. `snapshot()` 에 `home_failed` 를 노출한다.

**Seer 가 다시 호밍해도 래치는 풀리지 않는다** — 우리가 관측할 수 없는 사건이기 때문이다.
해제 수단은 `~/home` 재수행뿐이다.

## Alternatives (기각)

- **`homed_effective()` 에서 ②를 없앤다** — Seer 호밍 인정이 깨진다. 2026-08-04 에 그것 때문에
  바퀴가 안 움직인 실기 사고가 있었고 `README.md:237` 이 「재호밍 불필요」를 약속한다. 기각.
- **호출부(각 클라이언트)가 `~/home` 응답을 확인하게 한다** — 지금 필요한 규율이지만 강제가
  안 된다. 다음 호출부가 생기면 같은 구멍이 다시 열린다. 게이트에 두는 쪽을 택한다.
  (호출부 규율은 이것과 배타적이지 않다 — `steer_to_zero()` 구현 시 성공 분기 강제는 별건.)
- **bit15 0→1 전이를 관측해 「누군가 재호밍했다」로 래치를 푼다** — 폴 주기(50 ms)보다 짧은
  전이를 놓치면 조용히 안 풀리고, 놓치지 않으면 조용히 풀린다. 어느 쪽 실패도 화면에
  드러나지 않는다. 기각.

## Consequences

**이득** — 실패한 호밍 뒤 조향이 열리지 않는다. 게이트 하나에 있으므로 조향 경로 3곳과
앞으로 생길 `steer_to_zero()` 가 전부 자동으로 덮인다.

**비용** — Seer 가 복구 호밍을 해도 우리 쪽은 `~/home` 을 다시 돌려야 조향이 열린다.
그 재호밍은 **100°+ 물리 스윙**을 동반하므로 공짜가 아니다. 운용 중 이 비용이 실제로
문제가 되면 「운용자가 축 위치를 확인했다」를 명시적으로 받는 해제 경로(서비스·버튼)를
추가한다 — 지금은 근거 없이 푸는 자동 경로를 만들지 않는 쪽을 택한다.

**남는 위험** — 판다 직결·단독 GUI 는 이 게이트를 지나지 않는다. 그쪽은 시퀀서를 쓰지 않고
호스트가 `0x60FB:04` 를 직접 쓰며 완료 판정이 bit15 2상 관측(0 → 1)뿐이다. 그 경로에서
bit15 가 잘못된 원점으로 1 이 될 수 있는지는 **근거가 없어 주장하지 않는다.**

**미구현이 그대로 남는 것** — ADR 2026-08-08 §Decision 2 의 `steer_to_zero()`.
그것이 구현될 때 성공 분기 강제는 여전히 별도로 해야 한다 — 이 래치는 게이트를 닫을 뿐
호출부가 실패 응답을 읽게 만들지는 않는다.

## Rollback

가역. 되돌리려면 `backend.py` 에서 `_home_failed` 대입 4곳과 `homed_effective()`·
`_not_homed_reason()` 의 분기, `snapshot()` 의 키 1개를 제거하고
`test_backend.py` 의 「실패한 호밍 뒤 …」 6건을 삭제한다. 영속 상태·스키마·펌웨어 변경 없음.
