# CAN Relay 펌웨어 신규 작성 가이드

작성 2026-07-28. 기존 펌웨어를 참고 구현으로 두고 **새로 작성**할 때의 규약이다.

---

## 1. 목적

Seer 컨트롤러와 모터 드라이브 사이에 끼어들어 **PC(Personal Computer)가 Seer 대신 모터를 몬다.**
Seer 는 눈치채면 안 된다 — 알아채면 노드 상실 알람을 내고 재호밍을 걸어 조향축이 물리적으로 움직인다.

```
Seer ──bus0(CAN1)── [판다 릴레이] ──bus2(CAN3)── 드라이브 4대
                         │                       node1,2 구동륜 (PV 속도)
                     USB │                       node3,4 조향축 (PP 위치)
                       Orin
```

---

## 2. 안전 규칙

### 확정 (사용자 지시)

| # | 규칙 |
|---|---|
| **S1** | 전원 투입 후 PC 명령이 있기 전까지 relay 연결 금지 |
| **S2** | PC 와 통신이 없으면 relay off |

즉 **relay on 은 PC 가 살아 있는 동안만.**

### 추천 (미승인 — 채택 여부 결정 필요)

| # | 규칙 | 이유 |
|---|---|---|
| S3 | relay on 전에 모터 정지 확인 | 움직이는 중에 붙이면 그 순간 지령이 얼어붙는다 |
| **S4** | **relay off 전에 모터를 세운다** | **PC 가 마지막에 쓴 속도 지령이 드라이브에 남는다. 끊는다고 서지 않는다** |
| S5 | relay 실제 상태를 읽을 수 있어야 한다 | 명령만 내리고 결과를 못 읽으면 판정도 기록도 못 한다 |
| S6 | relay 전환은 반복 토글되면 안 된다 | 조건이 계속 참이면 계속 토글한다. 한 번 끊으면 래치 |
| S7 | 펌웨어가 멎으면 relay off | hang 시 붙은 채 굳으면 Seer 도 PC 도 모터를 못 쓴다 |
| S8 | relay 전환은 Seer 통신 틈을 노린다 | 전환에 ~11 ms 걸리고 그 사이 명령이 깨지면 Seer 가 노드 상실로 판단 |

**S4 가 가장 중요하다.** 나머지는 없어도 사고가 나진 않지만, S4 가 없으면 relay off 가 안전 동작이 아니다.

## 3. 과거 코드 참조 규칙 — 주석은 읽지 않는다

> **기존 펌웨어를 참고할 때 주석을 근거로 삼는 것을 금지한다. 기능은 코드로만 확인한다.**

이유는 실증돼 있다. `safety_seer_gate.h` 의 `0xec`(Seer 호밍 차단) 기능은
"제어권을 반환하면 Seer 가 `0x60FB.4=1` 을 보내 조향축을 137° 왕복시킨다"는 **주석을 근거로** 만들어졌는데,
실측 결과 그 현상은 존재하지 않았다 — 정상 운전 13,508 프레임 중 `0x60FB` 접근 **0건**,
그리고 137° 는 이상거동이 아니라 GOZERO 복귀라는 **설계 동작**이었다.
> ❌ 정정 2026-08-03: 도착점은 **조향 0° 가 아니라** 펌웨어 GOZERO 상수이며 0° 대비 +0.178°/+0.331° 다(10회 실측, 모σ 2.80/3.21).
저장소의 다른 모든 자료가 이를 올바르게 적고 있었고 **그 주석 하나만 반대로 말하고 있었다.**
후속 세션이 그 주석을 1차 근거로 재인용해 잘못된 판단을 확대재생산했다.

또한 폴 레이트 "12초 실측" 수치가 주석에 남아 있었으나 어떤 데이터로도 재현되지 않았고
(주석 226~243 Hz vs 실측 101.5 / 111.5 Hz), 주석 자신이 "원본 캡처는 보존돼 있지 않다"고 인정하고 있었다.

### 지켜야 할 것

| | 규칙 |
|---|---|
| 1 | 기능 판정은 **코드 실행 경로 추적**으로만 한다. 주석·docstring·`README` 는 근거가 아니다 |
| 2 | 숫자(임계값·주기·타임아웃)는 **상수 정의와 사용처**를 찾아 확인한다. 주석의 수치는 인용하지 않는다 |
| 3 | 하드웨어 거동은 **실기 조회·캡처**로 확인한다. 코드도 하드웨어의 근거는 아니다 |
| 4 | 드라이브·MCU 규격은 **1차 매뉴얼 원문**(`HB:줄`)으로만 인용한다 |
| 5 | 호스트 도구의 docstring 도 같다 — 코드와 어긋난 사례가 저장소 안에 이미 여러 건 있다 |

**"주석에 그렇게 쓰여 있다"는 어떤 결정의 근거도 될 수 없다.**

## 4. 작성 원칙 — 한 번에 하나, 반드시 실기 검증 후 다음

> **기능을 하나 넣을 때마다 빌드 → 플래시 → 실기 검증 → 기록 을 끝내고 다음으로 간다.
> 두 개를 한 번에 넣지 않는다.**

이유: 실기에서 문제가 나면 **어느 변경이 원인인지 갈라낼 방법이 이것뿐**이다.
이 저장소에는 `checks/`·pre-commit·CI 가 없고, 자동화 검증 자산도 fail-safe 를 끈 채 도는 벤치뿐이다.

### 각 단계의 필수 절차

| | 항목 | 통과 기준 |
|---|---|---|
| 1 | 빌드 | `-Werror` 통과 |
| 2 | **크기 확인** | 앱 영역 **49,152 B 이하**. 초과하면 서명검증 실패로 벽돌 (2026-07-27 실증) |
| 3 | 백업 | 플래시 **전** 현재 실기 이미지를 `fw_backups/` 에 보존. 파일명에 서명 md5 포함 |
| 4 | 플래시 | `flash_panda.py` |
| 5 | **실기 대조** | `0xd3`+`0xd4` 서명 md5 가 방금 빌드한 것과 일치하는지 조회. **파일이 아니라 장치를 조회한다** |
| 6 | 기능 검증 | 아래 §4 의 해당 항목 |
| 7 | 기록 | 무엇을·왜·어떻게 검증했는지. 검증 안 한 것은 "미검증"이라고 쓴다 |

**5번을 건너뛰지 않는다.** 스테이징 파일의 md5 를 보고 장치 상태를 단정한 오보고가 실제로 있었다
(`docs/claude-mistake/2026-07-28-011`).

## 5. 기능별 검증 방법

새 펌웨어가 넣을 기능을 순서대로 두고, 각각의 실기 확인 방법을 못박는다.

| 순서 | 기능 | 실기 검증 방법 |
|---|---|---|
| 1 | 부팅 시 relay off (S1) | 전원 인가 후 아무 명령 없이 `car_harness_status`·릴레이 상태 조회. Seer↔드라이브 통신이 정상인지 캡처 |
| 2 | relay on/off | `orin_gap_measure.py` — 전환 갭 측정. 기준값 engage ~11 ms / disengage ~10 ms |
| 3 | 투명 중계 | 권한 없는 상태로 intercept 유지하며 Seer 알람 0건 확인 |
| 4 | 기만 (캐시·동결·가짜 ack) | `orin_cover_test.py` — Seer 알람 52111/52106 미발생 |
| 5 | 전환 커버 | `orin_gap_measure.py` — 커버창 내 판다 bus0 송신이 있고 300 ms 에서 멈추는지 |
| 6 | **정지 (S4)** | **차체 부양 상태**에서 정지 수단 발행 → `0x6064` 시계열로 실제 감속·정지 확인 |
| 7 | 통신 두절 시 relay off (S2) | PC 프로세스 SIGKILL → 릴레이 개방 시각 + 모터 정지 여부 |

**6번을 접지 상태에서 하지 않는다.** 조향축이 최대 137° 움직인다.

## 6. 확정된 실측값 (설계 근거)

새로 작성할 때 이 값들은 재조사하지 말고 그대로 쓴다. 전부 2026-07-28 실기·원문 확인.

| 항목 | 값 | 출처 |
|---|---|---|
| 하드웨어 | Black Panda (STM32F4 / bxCAN) | `get_type()` = `\x03` |
| CAN 속도 | 250 kbps | `can_common.h` |
| node guarding | 4노드 전부 `0x100C=500` ms, `0x100D=1` → **타임아웃 500 ms** | SDO 판독 |
| 가딩 폴 중단 시 | 드라이브가 **HALT, 모터 전원 유지**(토크 유지) | Handbook V7.0 §6.4.3 (printed 142) |
| 능동 정지 옵션코드 | 4노드 전부 `0x605A=0`, `0x605D=0`, `0x6085=0` → **거동 미정의** | SDO 판독 |
| `0x60FB.4 = 0` | 진행 중 모션 효과 **원문 미기재**, 실측 발행 0건 | Handbook + 캡처 327,945 프레임 |
| 릴레이 전환 갭 | engage **11.6 ms** / disengage **10.2 ms** | `orin_gap_measure.py` 2회 |
| 전환 커버 | 300 ms, 경계 정확 (마지막 판다 응답 +299.5 ms) | 같은 도구 |
| 버스 트래픽 | SDO 요청·응답 + node guarding **셋뿐**. PDO·NMT·EMCY **0건**(데이터 프레임이라 캡처됨). **SYNC 는 「0건」이 아니라 계측 불가** — 캡처 도구가 DLC 0 프레임을 폐기하므로(orin_homing_capture.py:180 `or not dat: continue`) SYNC·Guard RTR 폴(둘 다 DLC 0)은 관측 자체가 안 됨 | 데이터(DLC≥1) 프레임 전수 분류 |
| 앱 영역 한도 | 49,152 B | 플래셔가 섹터 1–3 만 지움 |

### 미검증 — 아직 실기로 보지 않은 것

아래는 사실 상태를 기록해 둔 것이다. 이 중 무엇을 언제 확인할지는 별도 판단이며,
**여기 있다는 이유로 다른 작업을 막지 않는다.**

| 항목 | 현재까지 확인된 것 |
|---|---|
| 폴을 끊었을 때 실제로 500 ms 뒤 서는가 | Handbook 서술 + `0x100C/0x100D` 설정값까지. 거동 관측은 없음 |
| HALT 의 감속 프로파일·정지 거리 | 옵션코드가 전부 0. Handbook 에 값 의미 미기재 |
| 판다가 낸 가딩 폴로도 드라이브 타이머가 리셋되는가 | 미확인 |
| relay 물리 상태를 읽을 수 있는가 (S5) | SBU(Sideband Use) ADC 값이 릴레이 상태에 따라 달라지는지 미확인 |

## 7. 롤백

- 펌웨어는 **이미지 단위**로만 되돌린다. 부분 롤백 불가.
- 되돌린 뒤 반드시 `0xd3`+`0xd4` 서명 md5 로 **장치를 조회**해 복귀를 확인한다.
- 플래시 실패로 부트스텁에 갇히면 `flash_panda.py --recover`(DFU).
- 이미지 체인은 `Tools/Can_Relay/fw_backups/README-*.md` 에 기록한다.

## 8. 새 코드의 주석 규약

- **정정 이력을 코드 주석에 누적하지 않는다.** 코드에는 정본 1줄, 이력은 이 `docs/` 폴더에.
- 정정은 문서 **맨 위**에 쓴다. 아래에 붙이면 읽히지 않는다.
- 현행 펌웨어는 2026-07-28 에 주석 2,048건을 제거했고 `panda.bin` 바이트 동일로 기능 무변경을 증명했다.
