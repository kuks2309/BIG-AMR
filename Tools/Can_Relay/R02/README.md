## 런타임 검증 (2026-09-01)
- ✅ 펌웨어 설치·서명 검증 통과(앱 부팅 `0xddcc`·서명==파일).
- ✅ **passthrough RX 실기 확인** (2026-09-01 22:2x, SILENT·제어권 미획득, Seer 능동 구동 중 20 s):
  **bus0(Seer) 34,073 프레임 · bus2(모터) 34,072 프레임 · rx 에러 0**. ID `0x601~604`(드라이브 SDO)·
  `0x581~584`(응답)·`0x701~704`(하트비트). bus0·bus2 동일 트래픽 = passthrough 브리지 정상, 판다가 양쪽 탭.
  → 트랜시버 tap·종단·펌웨어 전부 정상. R01처럼 passthrough 에서 판다가 읽는다(insert-only 아님).
- 함정 주의: 초기 청취가 0 프레임이었던 것은 **그 순간 Seer 폴링이 비활성이던 타이밍**이었고 보드 결함이
  아니었다(에러 0 = 유휴 라인). 검증은 반드시 **Seer 능동 구동 중**에 할 것. can_send_errs 큰 값은 TX 실패가
  아니라 USB RX 큐 오버플로(고속 수신)로 정상 — [[biguamr-panda-health-counters]].
- ⚠️ **intercept(engage) — 미해결 (2026-09-01, 정지 로봇 다회 engage, PC 모션 미주입)**. `~/engage` 성공
  (제어권·릴레이 intercept 전환·fail-safe 무장)·클린 disengage·매번 Seer 회복. 릴레이 정상 스위칭(Seer 드라이브
  타임아웃 = 직결 끊김 증거). 그러나 intercept 시 Seer 가 비트 에러(Recessive·Dominant·Stuff)+ 랜덤 축
  타임아웃 + odo lost. **아직 정상 intercept 동작 못 함.**

  ⚠ **진단 경위 정정(중요)**: 초기 intercept 진단을 **결함 있는 노드 제어루프(`~/engage`)로 돌려 결과가
  오염**됐다. 그 노드는 engage 시 매 사이클 4축 전량 읽기+지령을 USB 로 하는데, 판다 USB 가 고속 포워딩 수신으로
  포화돼 **송신이 `LIBUSB_ERROR_TIMEOUT` 로 막힌다**(문제 A). 초기 호밍 abort·혼선은 이 **노드 코드 결함**이었는데
  종단·신호무결성으로 **성급히 오진**했다. → 진단은 결함 노드가 아니라 **직접·가벼운 제어로만** 할 것.

  **검증된 사실만:**
  - passthrough 4축 100%·0 에러 / CAN3 직접 폴 0 에러 → 모터측 버스·트랜시버·케이블 정상.
  - **A (USB 타임아웃)** = 노드 제어루프의 무거운 USB 탓. 직접 최소 USB(heartbeat+상태폴)면 안 나고 호밍도
    **DONE 3s** 성공(`direct_home.py`). → 노드 소프트웨어 결함(같은 F413·내장 USB 이므로 원 보드도 같은 부하면 났을 것).
  - **B (Seer 비트 에러·랜덤 타임아웃)** = 포워딩 자체. **노드 없이 직접 최소 USB 로 intercept 만 유지해도
    Seer 비트 에러 발생**(light_intercept.py, heartbeat 133회 무타임아웃인데도 Seer 54022 등). **A 와 별개,
    USB 볼륨으로 설명 안 됨.**
  - 종단 실험(net CAN1·net CAN3 각 상시 120Ω) 2회 모두 B 안 줄임(모터측은 passthrough 과종단 100→77%만) +
    250kbps 는 짧은 버스 종단 불량에 관대 → **B 는 종단 아님.**

  **미확정(추정 금지)**: B 의 근본 원인 = 보드 vs 펌웨어. ❌ **정정(2026-09-02, 실험결과 재대조) — 이전 서술
  「원 보드로 intercept 시 같은 비트에러 났는지 미확인(원 emulate 기록엔 55602만)」은 오기록이었다**: 원 보드도
  intercept 에서 같은 오류를 낸 적이 있다 — 2026-07-26 emulate 내구의 **첫 engage 전환에서 52111·52106·54022 stuff
  → 자동 재호밍(54301) → 52954 zeroing timeout**(field-record §14:177-180, seermon_endur.log 09:08), 그리고 부팅
  비트레이트(500k) 버그에서도 **54022 Bit Recessive**(issues_and_fixes:9). ⇒ **54022 는 R02 전용이 아니며 보드 쪽으로
  단정할 근거가 없다.** field-record 의 「engage 8/8·6h 52111/52106=0」은 그 문서 자신이 **「완전 해결」 철회·표본
  한정·'가동중' 미완주**로 강등했으니 「원 보드 intercept 깨끗」 근거로 인용 금지(§14:177·182).
  **실측된 유일한 차이**: 원 보드 오류는 대체로 **engage 전환 순간**(§8·emulate 09:08), R02 는 **정상상태 유지 중**
  (light_intercept)에도 난다는 것뿐 — 원 보드의 유지-깨끗은 §13:299 **15초 1회** 표본뿐이라 이 차이도 확정 아님.
  결정 실험(추정 대신): ⑴ R02 engage 전환 직후 모터 무응답 지속(ms)+52111/52106 동시 계측, ⑵ 원 보드에 athome_fix
  굽고 **동일 최소USB 유지 시험** 재현. 그 전까지 「보드」·「펌웨어」 어느 쪽도 확정 금지.
